# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An order-to-dispatch document management app for **Aglo Polymers Pvt Ltd** (Kolkata) — plastic preforms/caps/handles exported to Africa via Dubai/Mauritius intermediaries, plus domestic GST sales. The core domain is a chain of four documents, each created from the previous one with data carried forward:

**Quotation (revisions R1, R2… for negotiation) → Proforma Invoice → Order → Commercial Invoice → Packing List**

The proforma sits **before** the order, confirmed with Aglo on 2026-08-31 — the buyer is sent a proforma, pays the advance against it, and the order is booked from that. It used to be documented the other way round, and the app still holds the data that way: an order has no `pi_id`, so the link lives on `proforma_invoices.order_id` and is resolved backwards wherever it is shown. That is deliberate and load-bearing (`dispatchProgress()` walks it), not a leftover. What changed is which buttons the forms offer: a quotation converts to a proforma, a proforma books an order, an order raises the commercial invoice. Raising an invoice straight from a proforma is still offered, since a shipment can be billed without the order step.

**Team model:** six teams — **Super Admin, System Administrator, Sales, Logistics, Production, Quality** — from the RBAC matrix in the client's ERP specification (2026-09-10, superseding the access matrix of 2026-09-05) — each with full / view / no access per *function*. `services/permissions.ts` is the whole policy: pure, no `db` import, and the table written out in full rather than derived from defaults, for the reason `audit.ts` gives about its own `OWNER_SQL` — one wrong cell shows one person another's data. `users.team_role` is additive and carries **no CHECK**: SQLite cannot ALTER one, and `users.role`'s own CHECK — present on a database created from `schema.sql`, absent on one migrated from before roles existed — is exactly why this could not be done by widening that column. The legacy `role` is **derived** in `requireAuth` (`super_admin` ⇒ `manager`) and **never stored as a copy**: a stored mirror would let the Team page say *Logistics* over a row still saying `manager`, and that account would keep the database backup and every supplier rate — the same rule `qc.ts` states about a pass. Deriving is also what let this land in reviewable steps: every unconverted `requireManager` still means super admin, so anything missed fails **closed**. Guards come in two shapes — `requirePermission(fn, level)` for one function, and `requireFunction(fn)` where a read needs `view` and a write needs `full`; the routers serving more than one function (work orders = job + output + QC, stock, products, masters) guard per route instead, because Quality writing a QC check holds only `work_order: view`. **Ownership is a Sales concept**: `visibleCustomerIds` restricts `sales` alone, and the factory teams see every order — Production cannot make what it cannot see. That widening was only safe because **every router was function-gated first**: that one line used to be the entire barrier in front of every quotation, proforma, payment and PDF, and unscoping three teams before the gates would have put every price the company has quoted on the shop floor. Measuring found the two places it leaked anyway — `routes/pdf.ts`, where scope had been doing document-type duty and every builder now names its own `fn`, and `GET /api/audit/:entity/:id`, where a production login could read a quotation's price history until `ENTITY_FN` made a record's history follow the record's own function. A third: mounting on `view` alone let Logistics edit an order it may only view. Verified on a scratch instance across all five logins, seventeen endpoints and the leak checks. The client is handed its **computed capability map** by `/auth/me` rather than a copy of the table — there is no shared package, and a copy is a second policy that drifts — and `useCan()` returns a *function*, because `Layout` filters a whole nav array. A team with no Dashboard lands on the first screen it can use rather than on a page whose every figure answers 403.
- **The RBAC matrix now comes from the ERP specification of 2026-09-10**, which supersedes the access matrix of 2026-09-05 — the two disagree, and the client chose the newer. Its four columns are *modules*, and every cell carries a parenthetical naming what to read: *Read Only (View SO Demand)*, *(Verify COA Clearance)*, *(View WO Status)*. **The parenthetical is read as the specification, not the module header** — so Production reading the Sales module means the **order**, not the price quoted for it; a price readable from the shop floor is the leak `routes/audit.ts` records closing, and the narrow reading is the safe direction. Functions the spec's four columns do not name — `customer`, `product`, `master`, `dashboard`, `followup`, `payment`, `purchasing` — are **reachability** and stay at whatever lets each role work its own module: silence about a function is not an instruction to refuse it, and refusing `customer` to Quality would refuse Quality its own module, a check hanging off a work order that hangs off an order that names a customer. Three cells changed capability rather than merely widening a read, and each is worth knowing. **Sales approves now** (`approval: full`, from *"Full Access (Create/Approve Quotes, SO, Invoice)"*): `mayApprove` reads exactly that cell, so a quotation no longer waits on the owner — measured, a Sales login submits and approves its own and the document comes back `approved`. **Logistics lost invoicing** (`invoice: full → view`): the old matrix gave that role export invoicing and the new spec makes the whole Sales module read-only for it, so `exportOnlyInvoice` stays in the code but can no longer fire, there being no write left to narrow — measured, Logistics reads the list 200 and is refused a POST 403. And **Logistics gained `qc: view`**, which is the spec's *Verify COA Clearance* step before dispatch. One cell the spec asks for has **nothing to grant**: *View FG Inventory* for the Dispatch Lead, there being no finished-goods ledger (`material_moves` is raw material) — granting `material` instead would be granting a different thing from the one asked for. The COA had nothing to grant either when this landed and now does: it is `qc`, which the Dispatch Lead holds, so that step needed no further widening.
- **`sys_admin` is the spec's administrator row, and it is a sixth role rather than a rewrite of `super_admin`.** Read literally, *"User Management Only"* on all four modules would have left the owner's own account unable to open a quotation, an order, an invoice or a dispatch — so the client's call was to keep `super_admin` as it is and add the restricted row beside it, for whoever should be held to the separation of duties. It holds `team`, `settings`, `backup`, `audit` and nothing else that carries business data; **`master` is granted and `product` refused**, which is the one pair worth stating, because both look like reference data and only one is: locations, machines, moulds and processes are plant *configuration*, while the catalogue carries `unit_price`. `legacyRole` maps it to **`employee`**, so any guard still written as `requireManager` fails closed for it. Two things had to follow it. `GET /settings/sequences` was the last `requireManager` an administrator would meet, so a `sys_admin` could set a counter and not read it — it now carries `requirePermission('settings', 'full')` like the PUT beside it. And **`LANDING` in `App.tsx` gained `['team', '/team']`, last**: the list exists so a team without a dashboard opens on a screen it can use, and this role matched none of its entries, so it would have landed on the dashboard it holds `none` on — the very failure the list prevents.
- **Applying the matrix found a mount that silently pre-empted three route guards.** `/api/work-orders` was mounted `requirePermission('work_order')`, and that router serves **three** functions — `work_order`, `output` and `qc`. So a Dispatch Lead holding the new `qc: view` was refused the QC register **403 before the route's own `requirePermission('qc')` ever ran**, which blocked exactly the *Verify COA Clearance* step the spec puts in front of dispatch. This is the inverse of the trap `routes/pdf.ts` records: there a mount was too weak, here it was too specific. The mount is now `requireAuth` alone and **every route inside carries its own guard** — the two reads that had been leaning on it, `GET /` and `GET /:id`, now name `work_order` themselves, so nothing is opened by removing it. Verified across all six logins and fifteen endpoints, before and after: the QC register went 403 → 200 for Logistics while the job list stayed 403, and no other cell moved. `permissions.test.ts` grew from 11 cases to 13 — the administrative-functions test now enumerates which two roles own the system functions and asserts `approval` belongs to Sales and the super admin alone; a new case asserts the System Administrator reaches **no** business data (eighteen functions, plus `product` refused where `master` is granted); and another asserts the floor sees demand and never a price, so reading the module header instead of the parenthetical trips a test with the reason on it.
- **Nothing ships until it has passed QC** (`qcBlockError` in `services/qc.ts`, guarding `POST` **and** `PUT` on despatches — a despatch created with one innocuous line and then edited would otherwise walk through a POST-only gate). Shaped like `linkError`: a function returning the sentence to refuse with, so the rule is testable without the HTTP harness this codebase does not have. Three things it has to get right, each a way to be silently wrong. **A product with no specification is never blocked** — `has_spec: false` means nobody has said what to measure, the rule this module states twice about itself, and blocking those would have stopped every despatch on the day it shipped. **A check with nothing measured is not a pass**, which is why it asks `decorate` rather than rewriting the verdict in SQL — a second definition of "passed" would drift from the one on screen. And **the line position counts charge lines**: `work_orders.order_line` is numbered over *all* order items and charges are dropped afterwards, so an order opening with freight has its first goods line at position **1**; numbering after the filter gates the wrong line and no ordinary fixture catches it. A spec'd line with **no work order at all** is blocked, since not raising a job would otherwise be the way around the gate — the decision most likely to want revisiting, bought-in goods having no work order by nature. Every outgoing document (quotation/PI/invoice) must reach `approval_status = 'approved'` before its status can move to an outgoing value — see `server/src/services/approval.ts`, which owns that rule; unapproved PDFs get a watermark. Editing an approved document resets it to `not_submitted`.

- **Nothing is invoiced until it has passed QC** (the `qc` rule in `services/documentChecks.ts`, asked for 2026-09-10). The Hard Stop in the client's ERP specification: *"prevent the issuance of a Commercial Invoice **or Gate Pass** unless the corresponding batch status is marked as QC_PASSED"*. **The gate-pass half was already covered, and transitively rather than by a second guard** — a challan prints for a despatch, and `POST`/`PUT /despatches` have carried `qcBlockError` since they were written, so there was nothing to add there. The invoice half was covered nowhere: one could be raised, approved and sent for goods nobody had inspected, and neither `routes/invoices.ts` nor this table mentioned quality. **It gates approval, not the save**, which is what *issuance* means here and is the whole reason this table exists: refusing to create the row would stop the office drafting an invoice while the floor finishes inspecting, which is ordinary work, whereas refusing to *approve* it stops the document going out — `approval.ts` guarding every outgoing status behind exactly that. So one rule reaches all four routes into `approved` for free, and rides `getFull` as a finding above a disabled button rather than springing a 422 on a press. **`qcBlockError` is asked rather than restated**: it owns what a pass means, and a second definition for the invoice is precisely how the two would come to disagree — the thing `qc.ts` says twice about itself. It gained a `context` parameter supplying the two words the sentence needs (*dispatched* / *invoiced*) and nothing else. Three cases it deliberately does **not** block, each of which would otherwise have refused a legitimate invoice on the day it shipped: an **invoice with no order behind it** (nothing was produced against it, so there is no job to have inspected — the silence-is-not-failure rule `has_spec: false` states; the order is reached the way `dispatchProgress()` reaches it, the invoice's own `order_id` or backwards through the proforma's); a **line past the end of the order**, which has no counterpart to check, the rule the 10% variance report already follows about the same mismatch; and a **product with no specification** or a **charge line**, both inside `qcBlockError`, which is the point of asking it. A **proforma is never asked at all** — it is raised before anything is made, and gating it would refuse every advance this business collects. Measured over HTTP on a scratch instance: with a spec'd line and no passing check, `submit` **422**, `approve` **422**, `POST /status dispatched` **409** and the lorry **409**, each naming the line and saying what to record; a **failing** check (30.5 mm against a 27.9–28.1 tolerance) leaves it 422, because a failed check is not a pass; a passing one opens all four (200 · 200 · 200 · 201); and an invoice with no order behind it submits 200 throughout. Nine cases in `documentChecks.test.ts`, most of them asserting what is *not* blocked — a blocking rule that fires wrongly stops a shipment. **What the spec asked for and this did not do was the COA** — there was no batch and no certificate, so the gate was as strong as the QC record allowed and no stronger. The entry below adds both, and the rule now prefers a cleared lot where one exists while falling through to this one where none does.
- **Building it found a trap that would have had no way out.** `work_orders.product_id` came from the request body alone and was never derived, and the two readers of it disagree: `qcBlockError` asks whether the **order line's** product carries a specification, while `POST /work-orders/:id/qc-checks` builds the allowed parameters from the **job's**. So a job raised without a product against a spec'd line was blocked with nothing that could unblock it — the gate said a passing check was needed and the check route answered *"That check is not on the specification for this product"*. It was latent while only the despatch register asked; the invoice gate makes it reachable twice, so `POST /work-orders` now falls back to the product on the order line at that position, by the chain's own index rule. Strictly a fallback — a body naming a product still wins, and the order page has always sent one — so nothing that worked before changes. Measured: a job raised with no `product_id` comes back carrying the line's, and both checks then record 201 where they had answered 400.
- **A lot, and the certificate that clears it** (`services/batch.ts`, `batches` + `production_entries.batch_id` + `qc_checks.batch_id`, asked for 2026-09-10). The spec's §3 traceability chain and its *Final COA Approval* step, and the previous entry's closing sentence — *"what the spec asks for and this does not do is the COA"* — is what this answers. **A batch hangs off a work order**, which is the only batch this app can honestly hold: the specification uses two framings, a production run and a finished-goods lot picked from inventory, and **only the first is buildable** — there is no finished-goods ledger to pick a free-standing lot out of (`material_moves` is raw material, the same gap the RBAC matrix's *View FG Inventory* cell has nothing to grant against). Through the job a batch reaches the order line, the order, the customer and the product, which is §3's whole chain bar the dispatch leg. **Almost nothing is stored**, the rule `production.ts` and `stock.ts` both follow: what a lot made is the sum of the shift entries filed against it, so deleting a mis-keyed shift corrects the lot by construction, and whether it passed is read from its final check's own readings **through `decorate`**, so there is one definition of a pass and the gate and the screen cannot disagree. What *is* stored is the COA, because issuing one is an **act** rather than an observation — somebody cleared this lot, on a date, under a number that may already be with the customer. `OpenBatchModal` therefore asks two fields and says out loud that there is no quantity to type.
- **The spec's two QC levels are one nullable column.** `qc_checks.batch_id` blank is an in-process check against the job — what the register has always recorded — and one naming a batch is a **final** check on that lot. So *"an in-process check does not certify a batch"* is enforced by the column rather than by a rule that could be forgotten, and every check already on file stays exactly what it was. The verdict of a lot is the **latest decided** final check, which is deliberately *not* `qcBlockError`'s rule for a job: a job accumulates in-process checks and one pass is evidence the line can be made, while a lot is a thing that is **re-tested after rework** and the last word about it is the one that counts. A check with nothing measured is no verdict at all — `decorate`'s rule, not a second one — so re-testing is what changes a failed lot and an unmeasured check cannot quietly overwrite a real verdict.
- **`coaBlockError` is the fourth guard of its shape** (after `lockError`, `qcBlockError` and `incompleteError`) — a function returning the sentence to refuse with, testable without the HTTP harness this codebase does not have. Four refusals and **the order matters**, the most specific reason being the one worth reading: a lot **already certified** is never certified again (the rule every issued number here follows — a second certificate makes *"which COA covers this box"* unanswerable), a lot **nothing was booked into** is a number with no goods under it, a lot **never finally checked** is refused with what to do rather than with a verdict (silence is not a failure), and a lot whose final check **failed** is refused outright.
- **The invoice gate now prefers a cleared lot, and falls through where there are none.** `lotsForLine` in `qc.ts` asks whether the order line's job has batches at all: if it does, **one cleared lot is enough — not all of them**, because a partial shipment is normal and this book is full of them; if it has none, the line falls through to the job-level rule exactly as before, so **nothing already on file changes its answer** and the gate is as strong as the record allows and no stronger. It lives in `qc.ts` rather than beside the batch code because **`batch.ts` imports `qc.ts` and `qc.ts` may never import `batch.ts`** — the circle `documentChain.ts` already has to work around. The refusal's wording follows the record: with no batch it still says a passing check is needed, and with one it says *"no batch of it carries a Certificate of Analysis"*.
- **Who may open a lot and who may certify one are different questions**, and the spec answers them differently. Batch CRUD is `output: full` — opening a run is a production act — while **issuing the COA is `qc: full`**, the specification giving *Final COA Approval* to Quality. Measured across all six logins: issuing is 403 for Sales, Logistics and Production, and 409 *(already certified)* for the Super Admin and Quality, which is the two roles that hold the cell meeting the one-certificate rule rather than the permission gate. **Printing is not issuing** — `/api/pdf/coa/:id` carries `fn: 'qc'` and its own `partySql` (a batch has no `customer_id`), so Logistics reading it before dispatch is the spec's *Verify COA Clearance* step and is correctly 200 for all four roles holding any `qc`. `batch` and `coa` are the ninth and tenth `DocType`s (`B/{FY}/{SEQ}`, `COA/{FY}/{SEQ}`, derived per company like every other series).
- Verified over HTTP on a scratch instance: batch **`B/26-27/001`** made 120,000 from two shifts while output booked against no lot stayed out of it; an in-process check left the lot reading *none*; each of the four refusals fired in its own order; **`COA/26-27/001`** was issued by Demo Quality and a second attempt refused; the invoice then submitted 200, approved 200 and the lorry went 201, where before the certificate the gate had named the line; and the PDF came back 200 / 25KB as *Certificate of Analysis_Bharat Engineering Works_COA-26-27-001.pdf*. `batch.test.ts` is new — thirteen cases, most of them asserting that moving the facts moves the figures. The two things it left open are the two entries below: the dispatch → batch link, §3's last leg, and the loop that closes over a failed lot.
- **Which lot went on which lorry** (`despatch_batches`, the *where a lot went* half of `services/batch.ts`, asked for 2026-09-10). §3's last leg, and the thing the entry above named as missing: a batch reached the order line, the order, the customer and the product, and stopped there — so *which* lot was in a consignment, and where a given lot ended up, were both unanswerable. **One fact is stored and the rest is derived**, which is what decided the table's shape. It holds a despatch and a batch and nothing else: no order line, because the batch's own work order names it — there is a test that moves the job and watches the reported line move with it — and **no quantity per lot**, because the despatch line already records the pieces sent against that line and a per-lot split would be a second set of figures with nothing to reconcile them against. The question a split would answer is *how much of this lot is left*, which is a finished-goods question, and there is no finished-goods ledger here to answer it. So this is **set membership** — which lots travelled — which is exactly what a recall and a certificate each ask. It hangs off the despatch rather than the despatch *item* for a mechanical reason worth keeping: `saveItems` deletes and reinserts every line on each save, so a child of a row that does not survive a save is a link that does not either.
- **The Hard Stop, asked of the exact lot.** `qcBlockError` could only ever ask the line-level version — *some* lot of this line is certified — and said so in its own comment, because nothing recorded which lot was loaded. Naming one makes the precise question askable, so `despatchBatchError` holds a named lot to exactly the specification's rule, in three refusals, most specific first: a lot **not on file**, a lot **made against another order** (a scoping hole as much as a traceability lie — it would put another customer's certificate on this consignment's paperwork), and a lot with **no COA**, which is the Hard Stop itself. Measured: naming the uncertified `B/26-27/002` is refused **even though line 0 has a certified lot beside it and the line-level gate passes**, which is the whole value of storing the link. It guards **POST and PUT** like its siblings, and answers **409** for all three — each is the record not supporting the claim, where `despatchLimitError` answers 400 for a figure that is simply wrong. **Naming no lots is always allowed**, and must be: every despatch on file names none, and batching is something a floor starts doing rather than something this imposes backwards.
- **Writing the tests found the guard dropping a malformed id instead of refusing it.** `uniqueIds` filters to positive integers — right for the writer, and wrong to read the guard through, because a bad id then vanished rather than being rejected: the trip saved, with the lot somebody meant to name silently absent from it. A traceability record that quietly loses an entry is worse than one that refuses, since nothing afterwards says anything is missing. The guard now validates **what was sent** and the writer still cleans what it writes.
- **The challan prints the lots, and the invoice deliberately does not.** The certificate states a batch number, and that number identifies nothing unless it appears on something the buyer receives — so the block goes on the one document that travels with the goods. An invoice can bill goods that went on three different lorries, so a batch list there would describe no single delivery. Measured on a rendered page: *BATCH `B/26-27/001` · CERTIFICATE OF ANALYSIS `COA/26-27/001` 06-09-2026 · GOODS MS Forged Flange DN100*, and a trip naming **no** lots prints exactly what it printed before — no empty box headed *Batch*, which would read as a fault rather than as an absence — which is what protects every challan already issued.
- **Read backwards it is the question a recall asks**, so `batchesFor` carries each lot's trips and the job's Batches tab has a **Dispatched** column: reference, destination, customer. Asked once per job rather than once per lot, the N+1 this codebase keeps bounding. Empty means only that nobody has named the lot on a trip — naming is optional, so it can never be read as *this lot has not shipped*. It also bought the batch delete its third guard: a dispatched lot is refused by name (*"has been dispatched on DC/26-27/002"*). In practice a shipped lot is always a certified one, which the existing guard already refuses — but a delete guard that covers a foreign key only by transitivity stops covering it the moment the other rule moves, and a missed reference reaches the user as *Internal server error*.
- **The picker shows the lots it will not let you send.** `order.batches` rides the order's `getFull` for the dispatch form, and an uncertified lot is **returned and drawn disabled with the reason** rather than filtered out: a picker that silently omits the batch somebody is looking for reads as a fault, where one saying *no COA yet — cannot be dispatched* says what to do next. The server refuses that same lot with the same reason, so the screen explains the rule rather than keeping a copy of it. Lots are **not prefilled on a new trip**, unlike the box counts beside them: a guessed box count sits next to the piece count that checks it, whereas a guessed lot number would put traceability on a challan nobody verified. The block is absent entirely on an order with no lots, so an unbatched order shows the form it always did. The key is gated on `allows(req, 'qc')` in the shape the invoice's `despatches` key uses — and **that gate binds on nobody under the current matrix**, which is worth stating rather than implying: measured across all five logins, every role that can read an order at all (super admin, Sales, Logistics, Production) holds `qc: view`, and Quality, which holds `qc: full`, holds `order: none` and never reaches the route. It is kept for the reason `exportOnlyInvoice` is kept — the rule lives where the answer is decided, so narrowing a cell later narrows this with it.
- Verified over HTTP on a scratch instance: all three refusals fire with their own sentences, a certified lot on this order records 201 and reads back with its COA and its derived line, a **PUT that omits `batch_ids` leaves the lots alone** while one sending `[]` clears them, the reverse lookup reports *DC/26-27/002 · Hazipur Depot · Bharat Engineering Works*, the delete is refused by name, and both challans render as described. Seventeen tests in `despatchBatch.test.ts`; **401 pass**. The loop that closes over a failed lot — refused a certificate, refused a lorry, and until the entry below, with nothing recording what became of it — is the next entry.
- **What becomes of a lot that failed** (`batches.disposition`, `dispositionError`, `LIVE_OK`/`LIVE_REJECT` in `services/production.ts`; asked for 2026-09-10). The spec gives this one sentence — *"Out-of-spec units are flagged to prevent downstream defect propagation, initiating rework or scrap procedures"* — and two of its three clauses were already true: a failed lot **is** flagged, and it already propagates nowhere, being refused a certificate, a lorry and an invoice. What was missing was the third: nothing recorded what was **decided**, so a condemned lot sat on the Batches tab for ever looking exactly like one nobody had got round to. **Two values, not four.** `''`, `rework`, `scrapped` — the specification's own two words, and deliberately no *quarantined*: the state that would name is already what `''` means on a failed lot, and `held` derives it (`qc === 'failed' && disposition === ''`). A third stored value would be a second name for the absence of a decision, and two ways of saying one thing is how the two come to disagree. No CHECK constraint, the rule `products.product_type` states; the route answers 400 naming the accepted values.
- **The two halves behave completely differently, and that is the whole design.** **Rework needs no machinery at all** — a lot's verdict is its *latest decided* final check, so putting one back and re-inspecting it already cleared it before any of this existed. What rework adds is the **record**: why the lot is still open, who said so, and when. Measured over HTTP end to end — a lot that failed at 30.5 mm was marked rework, re-inspected at 28.0, certified `COA/26-27/001` and shipped on `DC/26-27/001`, with every figure unmoved throughout. **Scrap is the half that moves figures**, because condemned goods stop existing: `LIVE_OK` drops them from **every roll-up of what a job has made** — `progressFor`, `progressForMany`, `productionByOrder`, the work-orders list, the order book's line state, the material shortfall and the dashboard. Without that the floor reads as further ahead than it is, and the buyer is short by exactly the quantity nobody re-made. Measured: scrapping a 60,000 lot took the job from **produced 85,000 to 25,000** and its balance from 15,000 to 75,000, and the resin required went **1,785 kg to 8,925 kg** — which is the buying decision the record exists to correct.
- **Condemned output becomes rejected output rather than vanishing.** Dropping it from both columns was the first cut and it is perverse: `reject_pct` *improves* when a whole lot is condemned, which is the worst quality outcome there is. Nothing was un-moulded, so `qty_ok + qty_reject` is unchanged and only which side of it the pieces sit on moves — measured, 0.58% to 70.76% on the same job. Written as one fragment shared by all the roll-ups rather than restated in each, the reason `despatch.ts` owns `SEA_LEG`. **The sixth reader deliberately does not use it**: `batchesFor` goes on reporting that the lot made 60,000, because *the job stops counting it and the lot remembers it* — otherwise "what did we scrap" has no answer anywhere.
- **Scrap is terminal while it stands, and withdrawable because it has no artefact.** A scrapped lot is refused a COA **however its checks later read** — which matters precisely because a verdict is the latest decided check, so a fresh reading would otherwise walk a condemned lot straight back to a certificate. It is refused a lorry too, and that guard is asked **before** the COA one, because a lot can be certified and *then* condemned (dropped in the yard) and would otherwise walk through on the certificate it still holds. But withdrawing a decision is always allowed: unlike an issued COA, a scrap has nothing out in the world, and a lot condemned by mistake with no way back would be the trap-with-no-way-out this codebase has built once already. The one thing refused outright is **ruling on a lot that has gone to the customer** — condemning it here would drop the order's made-figure for goods that physically shipped, which is the reverse of the defect scrap exists to fix; what happens to bad goods already delivered is a return, and this app has no shape for one, so it says so rather than lending the wrong word to it.
- **`qc: full`, like the certificate** — the spec has QC initiate this, it follows directly from a failed final check, and it is the one act that can condemn a day's output. Measured across all five logins: Sales, Logistics and **Production 403** (Production opens the lot and books its shifts and holds no `qc`), Quality and the super admin 200. Recorded the way the COA beside it is — who, when, and **why**, the note being the only part of a scrap decision nobody can reconstruct afterwards. The order's status is re-synced after one, since a line reading *made* on the strength of a lot just scrapped is exactly the status-contradicting-the-record failure `orderStatus.ts` exists to prevent.
- **Writing it re-found the `schema.sql`-runs-first trap the hard way, and this time it stopped the app booting.** The new index went into `schema.sql` beside the table it indexes, which is where an index belongs — except that file runs **before** any `addColumnIfMissing`, so on a database migrated from an earlier version `CREATE INDEX … ON batches(disposition)` names a column that does not exist yet. Measured on a scratch instance planted with a pre-migration `batches` table: the boot died with **`no such column: disposition`** — not a degraded feature, the whole app refusing to start against the live database. It now sits in `connection.ts` after the migration, which is exactly where the unique document-number indexes live and for exactly the reason recorded there. A fresh install was fine throughout, which is what made it invisible until the pre-migration case was actually built.
- Verified over HTTP on a scratch instance: the vocabulary refuses `quarantined` naming what it accepts, rework records and moves nothing, scrap moves all four figures, the COA is refused with its sentence, withdrawing puts every figure back, and a shipped lot refuses both decisions by name. Fifteen tests in `rework.test.ts`; **416 pass**. **Deliberately not built: a dashboard chip for held lots.** The count would need a third SQL copy of the *latest decided check* rule, and this codebase pays for a second only where paging forces it (`RESULT_FAILED_SQL`); `held` is instead computed once, in TypeScript, on the batch row itself, and the job's Batches tab says *Awaiting a decision* in amber. If plant-wide visibility is wanted later, the honest way is to page the batch list rather than to approximate the count.

**A document must be finished before it can be approved** (`services/documentChecks.ts`). `approval.ts` owns *who* may approve; this owns *whether there is anything worth approving*, and until now the two were one question — a quotation with no line items and a blank date could be approved and sent. **Two levels, and the split is the whole design.** A rule that **blocks** is one nobody could argue with: no lines, no date, a blank description, a document that is nothing but charge lines, and — on a proforma or invoice, where a sum is being demanded — a line with no quantity or a zero total. A rule that **warns** is one this desk might reasonably break: a missing GSTIN or per-line HSN on a domestic invoice, a blank customs header on an export, a proforma with no bank account when the advance is paid against it — **promoted to a block on 2026-09-07** at the client's word, the first warning to move and the one-word `level` change this table was shaped for. It is the rule with the least room for argument on a proforma: the document exists to collect an advance, and one that does not say which account cannot do the only job it has. It blocks on the **proforma alone** — a commercial invoice states an account too, but it is raised against goods already made and often settled from the advance banked upstream, so refusing one over a blank account would stop a shipment for a field the proforma has already carried. Measured on a scratch instance: all four routes into `approved` refuse with the same sentence (`submit` and `approve` 422, the two implicit-approval paths — setting a status and booking an order — 409), rejecting still works, stating an account opens every route, and a commercial invoice with a blank one still submits. The test fixture gained a `bank_account` for the reason it already carried `payment_terms`: a fixture has to be a finished document, so each test fails only in the respect it names. Warnings are shown on the form and refuse nothing. That split exists because **the client's list of mandatory fields was never supplied** — it is the open item on their 2026-09-05 checklist — so everything plausible is computed and on screen, and promoting a warning to a block is a one-word `level` change in the rule table. The asymmetry is the reason: guessing a blocking rule wrong stops a shipment, guessing a warning wrong costs a line of grey text. **What is deliberately not blocked** matters as much: a **price-only quotation** carries rates against no quantity at all and a quotation may total zero, both documented shapes that a naive "quantity and total are mandatory" rule would have refused on the day it shipped; a charge line needs no quantity of its own; and an **export** document is asked nothing about GSTIN or HSN, being zero-rated. `incompleteError` is shaped like `lockError` and `qcBlockError` — a function returning the sentence to refuse with — and it guards **all four routes into `approved`**, which is the part that is easy to get wrong: `POST /:id/submit`, `POST /:id/approve`, and both places a manager approves *implicitly*, inside `blockUnapprovedTransition` and `blockUnapprovedConversion`, checked **before** the `decide` call or the one path that approves as a side effect would be the way past the gate. **Rejecting is never blocked**, or an unfinished document would be stuck in `pending` for good. Answered **422**, not 409: nothing conflicts, the document is incomplete. The findings ride on each `getFull` so the form lists them above a disabled button rather than springing the 422 on a press — a button that fails when clicked teaches people to click it twice. Measured on a scratch instance: all four routes answer with the same sentence, the status is still `not_submitted` afterwards, rejection still works, finishing the document opens every route, an invoice carrying three warnings submits anyway, and an employee and a manager get the identical refusal — the manager has no way round it either.

Plus payment tracking (advances against the PI, balance against the invoice), follow-up reminders, and a dashboard. Multi-currency (INR/USD/EUR), GST (`tax_type`: `none` for exports / `cgst_sgst` / `igst`), and export fields (INCO terms, ports, containers, two notify parties, method of despatch, quantity tolerance, ARN).

The **product catalogue carries packing and loadability** — `pcs_per_pack` (pieces per box), `qty_20ft` and `qty_40ft` (boxes that fill each container size) — mirroring the user's own catalogue sheet. Those three columns are what make the catalogue importable from Excel and the Container Planner possible; they are not decoration.

**The four PDFs are modeled on real Aglo documents in `D:\Quotation Doc\`** (quotation → Sanya sample; PI → Emeraude sample; invoice + packing list → AP/EX-101 samples). When changing a PDF layout, compare against those files — they are the spec.

## Hard constraints

- **No native npm modules.** The machine has no C++ toolchain (better-sqlite3 failed to build). The DB is Node's built-in `node:sqlite` (`DatabaseSync`, synchronous API) — keep it that way. The bar for *any* new dependency is high: the .xlsx reader was written by hand (~200 lines over `node:zlib`) rather than adding a spreadsheet package, because the npm-hosted ones carry known advisories. Reach for Node's standard library first.
- **All money math lives in `server/src/services/totals.ts`** (`computeTotals`, `round2`). The client's line-item totals are display-only previews; the server recomputes on every save. Never persist client-computed amounts.
- **Schema changes must be additive**: extend `server/src/db/schema.sql` (fresh installs) *and* add an `addColumnIfMissing(...)` call in `server/src/db/connection.ts` (existing DBs). There is no migration framework.

## Architecture

**Server** (`server/src/`, Express + TypeScript, ESM with `.js` import suffixes):

- `routes/` — one router per entity. The three money documents (quotations, proformas, invoices) share the same shape: `listSql` join with customer name, `getFull(id)` returning header + items (+ payments/variance), a `saveItems()` that deletes-and-reinserts items inside `transaction()` and stamps server-computed totals onto the header row, a `POST /:id/status` endpoint with a per-type allowed list, and delete guards that 409 if downstream documents or payments reference the row.
- **Orders are the order book** (`routes/orders.ts`), modelled on the user's real tracking spreadsheets in `D:\Quotation Doc\*.xlsx`: intake fields (order_through, spoc, the customer's own po_number/po_date), a production plan (promised → scheduled → revised → actual), advance tracking, and per-line `code`/`supplier`/`scheduled_date`/`dispatched_date`. **Dispatch progress is derived, never stored** — `dispatchProgress()` walks every invoice reachable from the order (`commercial_invoices.order_id`, or via a PI with that `order_id`) and sums `invoice_items` **by line index**, the same index-matching rule `syncPackingList()` uses. Orders carry **no approval workflow** (they record the customer's commitment, not an outgoing offer) so their PDFs are never watermarked.
- **The Orders page reads the book three ways** — *Order lines* (the default), *By product*, and the original per-order table, chosen by `?view=` so a filtered view is bookmarkable. The first two come from `services/orderLines.ts`, which is the only place allowed to answer "every order line and how far along it is". Line rows mirror the desk's own sheet: one row per item, the order number repeating. **A line's state is derived** (`not_started → in_production → made → part_shipped → shipped`) from work orders, despatches and invoices — never typed, because the real sheet is full of rows still marked Pending that the Despatch sheet shows went out. **Charge lines are excluded outright** (`is_charge`), as in `goodsOnly()`. The per-product view groups on `product_id`, falling back to description + colour so a custom line still shows as itself. The subtle part: matching invoice lines to order lines is done with `ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY sort_order, id) - 1` rather than by reading `sort_order` directly — that **reproduces** `dispatchProgress()`'s index rule instead of assuming the two agree, and does it in one statement where calling `dispatchProgress()` per order would be N+1. The check that keeps them honest is that `/orders/lines` `billed` equals `/orders/:id` `qty_dispatched` on every goods line.
- **The invoice's 10% quantity-variance check matches by position**, like the rest of the chain. It matched on `description` until 2026-08-21, so rewording a line on the invoice silently emptied its variance row — the report came back clean because nothing matched, which is the worst way for a check to fail. Positions are **not** compacted first: a charge line keeps its slot so the goods after it still line up (the packing list's rule), and charges are skipped when reporting instead, since a percentage variance on freight means nothing. An invoice line past the end of the proforma has no counterpart and is skipped. `pi_description` rides along so the form can say when the two lines at one position read differently — index matching is an assumption, and that is where it would show.
- **The commercial invoice owns its packing list.** `syncPackingList()` in `routes/invoices.ts` runs inside the create/update transaction: it creates the packing list on first save and always rewrites its items from `invoice_items`, taking only packing values (packages, dimensions, weights, custom1..3) from `body.packing.items` matched **by index**. Deleting the invoice cascades to it. `routes/packingLists.ts` `saveItems()` honours the same rule for linked lists, so descriptions/qty can never drift. `/api/pdf/invoice-with-packing/:id` emits both documents in one file (invoice pages, page break, packing pages) with the invoice's approval watermark.
- **Enquiries are the front of the funnel** (`routes/enquiries.ts`, mounted at `/api/enquiries`, `services/enquiries.ts`). Deliberately thin: a note with a date and a customer, because the moment it needs line items and a price it is a quotation. The list's `quotation_count` is derived and **excludes superseded revisions**, so a renegotiation is not two answers. `quotations.enquiry_id` existed from the beginning and **nothing ever wrote it** — `enquiryLinkId()` now resolves it on create, requiring the enquiry to be in scope *and* on the same customer (`linkError`'s rule; 404 either way so an id cannot be probed for), and the **revise** INSERT carries it forward, without which the link died at the first renegotiation. `syncEnquiryStatus()` moves `open → quoted` when a quotation answers it, inside the same transaction: **forward-only, and `lost` is never touched**, the two rules `orderStatus.ts` follows — losing an enquiry is a decision, and quoting it later does not un-lose it. The seed's summary claimed five enquiries for a long time while writing none; it now writes four, including one already answered.
- **An invoice raised from an order must still carry `pi_id`.** With the process running proforma → order → invoice, `prefill/from-order` became the normal way to raise a commercial invoice, and it returned `order_id` and `quotation_id` but not `pi_id`. Two things hang off that column and both fail silently without it: `services/receivables.ts` credits a proforma's advance across **the invoices raised from that PI**, and the 10% quantity-variance check is gated on `if (inv.pi_id)`. Measured on a scratch instance — an invoice with the link showed €5,892 of advance applied and €27,953 outstanding, the same invoice without it showed €0 applied and the full €33,845 due, which is the customer being asked twice for money already banked. The endpoint now resolves the proforma backwards through `proforma_invoices.order_id` and returns its id. It is shared with the proforma form, where `pi_id` is meaningless and `headerValues` drops it.
- **The chain is one way, and converting a document locks it** (`services/documentChain.ts`). Raising a proforma from a quotation sets that quotation to `accepted`; booking an order from a proforma sets it to `in_production`, labelled *Sales Order Generated*. Both are one guarded UPDATE in the shape of `syncEnquiryStatus` — **forward-only**, so `rejected` and `cancelled` are never touched (a decision, not an observation) and a proforma already at `advance_received` is not dragged back. **Locking is derived, never stored**: a quotation is locked because a proforma names it, a proforma because it carries an `order_id`, so deleting the downstream document unlocks it and there is no override. `lockError()` guards the document's *content* — PUT, status, revise, approval — and deliberately **not** the things that carry on afterwards: **a payment is banked against the proforma after the order is booked**, which is the normal case and the whole point of an advance; internal notes have their own PATCH for exactly this reason; duplicating, following up and printing change nothing. The proforma's **status used to be exempt too, and that exemption expired**: it was written when `advance_received` and `in_production` both came *after* the order existed, so refusing them would have blocked the normal way forward. Neither is true now — the advance is banked against the proforma **before** the order is booked, and `in_production` *is* the booked state, set by `syncProformaOrdered` rather than typed. What was left was a pill row that could contradict the order sitting downstream of it, on the one document whose content is otherwise frozen; the user found it by clicking it. `POST /proformas/:id/status` now carries the same `lockError` the quotation's has always had, and the client hides the pills and disables the list's picker rather than leaving the 409 to be discovered. The escape is the one every lock in this chain has — delete the order — and a deal that dies after booking is **cancelled on the order**, which carries its own `cancelled` status and is deliberately never frozen. Verified both ways on a scratch instance: all five settable statuses answer 409 while the order stands, and the proforma is settable again the moment it is deleted. **A lock nobody can see reads as a fault**, which is how the user found the second half of this: six proformas all saying *Order confirmed*, two of them with the picker greyed out and nothing on the row to say why. Two causes, and both had to go. The list never showed the order at all — the spreadsheet export has had an `Order` column all along, the table did not — so it now carries one, beside the status rather than in the export's identity group, since the order *is* the reason the pill next to it is frozen. And the rows themselves were stale: `syncProformaOrdered` set `order_confirmed` until 2026-09, so a proforma with an order booked read exactly like one with nothing booked, and the status that would have explained the lock was never set. A one-off pass in `connection.ts` moves any proforma holding an `order_id` to `in_production`, using `syncProformaOrdered`'s own guard copied rather than imported (`documentChain.ts` imports `db` from that file — keep the two in step). It fills `status_before_ordered` exactly as the live path does, so deleting the order still puts the proforma back where booking found it, and it is idempotent because `in_production` is not in the guard. Measured on a scratch instance planted with the screenshot's state: the row moved to `in_production` remembering `order_confirmed`, deleting the order returned it to `order_confirmed`, a second and third boot moved nothing, and a `cancelled` proforma carrying an order was left alone. Two traps found by testing it. **The order's delete guard counted proformas pointing at it** — written when the chain ran order → proforma, where such a proforma really was downstream. With the direction reversed that count deadlocked the two guards against each other: the proforma was locked by the order and the order could not be deleted because the proforma pointed at it, so nothing could ever be unlocked. The delete now releases the back-pointer (`order_id = NULL`) the way deleting a quotation clears `superseded_by`, and only a commercial invoice blocks it. **Locking a document is not the same as refusing to convert it twice**, and the gap between the two let a quotation be converted again after it was locked. `lockError` guards *changes* to the quotation, and raising a second proforma changes nothing about it — it writes another row naming it — so nothing refused, and the form went on offering **→ Create Proforma** beside a banner calling that quotation converted and read-only. **`alreadyOrderedError` is the same guard one step down the chain**, and it was failing more quietly: `POST /orders` claims a proforma only when `order_id IS NULL` — right, since re-pointing it would orphan the first order's dispatch figures — but the order was still *created*, just with nothing linking it back, so a second booking looked like it worked and left an order outside the chain that `dispatchProgress()` cannot see. Measured before the fix: two orders on file, one of them unlinked. It refuses on the prefill and on the create, deleting the order still releases the back-pointer and lets a fresh one be booked, and `Duplicate` still raises a second proforma with `order_id` dropped. **And a proforma whose order is deleted goes back where booking found it** — `status_before_ordered` (additive, as every schema change must be) plus `syncProformaUnordered`, called inside the delete transaction *before* the back-pointer is released, since it is keyed on `order_id`. Same shape and same reasoning as `status_before_paid` and `status_before_completed`: everything below this only accumulates, but an order can be deleted, and a status left claiming *Sales Order Generated* for a document that no longer exists is worse for looking automatic. Guessing was not an option — measured, a proforma booked from `sent` goes back to `sent` and one booked from `advance_received` to `advance_received`. **Only what this code moved is moved back**: the column is written by `syncProformaOrdered` and by nothing else, so a row that reached `in_production` by hand — every one on file, booking only having started setting it in 2026-09 — has nothing remembered and stays put. Setting the status by hand **clears** the memory, the way `POST /quotations/:id/status` clears `status_before_expired`, or deleting the order later would overwrite a choice made after it was booked. `alreadyConvertedError` closes it on both the prefill and the create (the prefill being a GET the form can be got past), and answers **409 naming the proforma that already exists** rather than the proforma → order side's quieter "don't claim it": the caller asked to convert *this* quotation, and an unlinked proforma is a worse outcome than being told why not. Two proformas both claiming to be the one raised from a quotation is what makes "which document came from this quote" unanswerable — the same reason `duplicate` refuses to carry `quotation_id`, and the reason `quotationLockedBy` can take the first row and be right. Client side the button becomes a **link to the proforma**, which is the shape the proforma's own "Book Order" button already had. A second offer to the same customer is `Duplicate`, which still works on a locked quotation, and deleting the proforma still unlocks everything — verified both ways. And **conversion requires approval first** (`blockUnapprovedConversion`), or converting a draft would freeze it as a draft, watermarked PENDING APPROVAL, with no way left to fix it — it borrows `blockUnapprovedTransition`'s best trait, that **a manager converting an unapproved document approves it in the same action**, and takes a `commit` flag because the prefill endpoints are GETs and a GET must not approve anything as a side effect.
- **An export quotation converted to a *domestic* proforma** (found by the user 2026-09-10, `routes/proformas.ts`). `prefill/from-quotation` derived the type from **`customers.country`** and ignored `q.is_export` entirely — so an export quotation raised for a buyer registered in India came back domestic. That is not a corner case on this book: Aglo exports to Africa **through Dubai and Mauritius intermediaries**, and a merchant exporter or an Indian-registered buying house is an ordinary customer. The sibling endpoint had it right all along — `prefill/from-order` reads `o.is_export` and nothing else — which is what marks this as an oversight rather than a decision. **A stated fact beats a derivation**: somebody chose the type in `NewDocumentDialog` before the quotation existed, and that choice had already settled the quotation's own tax treatment and export fields; the country is the hint `fromCustomer()` uses when there is nothing better, and here there is something better. The rule is now `Number(q.is_export) === 1`, full stop.
- **What made it expensive is that it cannot be undone.** The proforma draws its number from whichever series the flag names, and `exportChangeError` then refuses to flip it — rightly, since the number may already be with the customer. Measured before the fix on a scratch instance: an export quotation for an India-registered buyer produced **`AGLO/PI/26-27/001` out of the domestic series**, carrying `tax_type: none` on a domestic document, no country of origin and no quantity tolerance, and the PUT that would have corrected it answered **409 — *"This document was numbered AGLO/PI/26-27/001 from the domestic series, so it cannot be switched to export."*** After the fix the same quotation produces **`AGLO/EX/26-27/002`**, `is_export=1`. All four combinations were measured: export quote + Indian buyer → export (the fix), export quote + blank country → export, domestic quote + Indian buyer → domestic, and **domestic quote + German buyer → domestic**, which is the one behaviour that *changed* — the old guess would have made it an export proforma against what the person chose on the quotation. **`npm run check-series` will not find the documents already affected**, and that is worth knowing: it compares a number against its own row's flag, and on these two agree — both say domestic. The mismatch is against the quotation upstream, so it is found with `SELECT … FROM proforma_invoices p JOIN quotations q ON q.id = p.quotation_id WHERE q.is_export = 1 AND p.is_export = 0`. A row it returns cannot be repaired in place; raise a fresh proforma of the right type, or correct the Number by hand if the series alone is wrong.
- **The commercial invoice is raised from the order only.** `invoices/prefill/from-proforma` is gone: billing straight from the proforma skipped the order — the document that knows what was actually made and shipped — and let one shipment be billed by two routes. The order route is `proformas/prefill/from-order/:orderId`, which resolves the proforma backwards and returns its `pi_id`, so the advance allocation and the variance check still work.
- **Carry-forward pattern**: each conversion is a `GET /prefill/from-<source>/:id` endpoint returning a draft payload (never writes). The client form loads it via `?from_quotation=` / `?from_proforma=` / `?from_invoice=` query params and the user saves normally. Follow this pattern for new conversions. **Booking an order from a proforma is the one conversion that writes back**: an order has no `pi_id`, so the link lives on `proforma_invoices.order_id` — the prefill echoes `pi_id`, and `POST /orders` sets it, **only when that proforma is unattached**, since re-pointing it would orphan the first order's dispatch figures. It is also the reason `dispatchProgress()` works unchanged. The **advance is not copied across — it is derived** (`orderAdvance` in `services/receivables.ts`, on the order's `getFull` and its PDF; asked for 2026-09-07). It used to carry across not at all, on the reasoning that a copy would show the same money twice; what was missing is that the order has three advance columns of its own and somebody had to type into them. Deriving answers both. An order has no `pi_id`, so this resolves the proforma backwards through `proforma_invoices.order_id` — `dispatchProgress`'s own walk — and asks `proformaAdvance`, which owns the currency rule, so the order page, the proforma page and the order PDF quote **one** figure rather than three. **The timing is the argument for deriving rather than prefilling**: the advance is normally banked *after* the order is booked, which is why `lockError` deliberately leaves payments alone on a locked proforma — so a figure copied at booking would read zero on almost every order and stale on the rest. Measured on a scratch instance: an order booked from a ₹1,18,000 proforma shows nothing, then ₹10,000 the moment a payment is recorded, then ₹35,400 on the second, then **₹10,500 again when one is deleted** — which a stored copy could not do. The **date of credit is the most recent payment that actually counted**, so a payment in another currency can neither add to the figure nor date it; that path is covered by `orderAdvance.test.ts` rather than over HTTP, because `POST /payments` takes its currency from the document and cannot create a mismatched one. **Advance *Due* is prefilled, not derived** — it is a commitment that can be renegotiated, so `advanceDueFrom` reads the percentage out of the proforma's own payment terms (*30% Advance and Balance before Dispatch* → 30% of the total, measured at ₹35,400) and leaves it editable; a credit term names no percentage and prefills nothing. The three columns stay and an order with **no** proforma keeps its typed boxes and prints them, so nothing already on file changes. **It is derived in both directions**, which the first cut missed: `orderAdvance(orderId)` resolves the proforma backwards from a saved order, and `advanceForProforma(piId)` — the same block, split out — answers for the order *being booked*, since `prefill/from-proforma` runs before any order row exists. Without it an advance paid **before** the order is raised read as zero on the very screen where the order is created, which is where it was noticed. It rides the prefill as `advance`, held aside from the draft rather than spread into it, because there is nothing to store and it must not travel in the save payload. Measured: a proforma part-paid ₹35,400 before booking prefills that figure, the saved order still reports it, `advance_amount` stays **0** — nothing was copied into the column — and a prefill from a *quotation* carries no `advance` key at all.
- **A new line starts at 18% GST** (`DEFAULT_TAX_PCT` in `components/LineItemsEditor.tsx`, asked for 2026-09-06). Every line was created at 0 and typed over, on a catalogue where 18% is the answer for essentially everything — so the field existed to be corrected rather than filled in, and a line left at zero silently under-charges the tax on a domestic invoice. It is applied whatever the document type, which is safe rather than sloppy: `computeTotals` reads `tax_pct` **only when `taxType !== 'none'`**, so an export document ignores it and hides the column anyway (measured — an export quotation with a fresh line shows no Tax % column and `Lines: €0.00`). It also means a saved quotation flipped from export to domestic already carries a rate rather than a row of zeros. A **default, not a rule**: the field is in the row and editable, and nothing already saved changes — a line stored at 0 stays at 0.
- **And it starts on the basis this catalogue is quoted on** (`DEFAULT_UNIT` in `components/LineItemsEditor.tsx`, asked for 2026-09-06). A new line opened on `unit`, which is the same defect `DEFAULT_TAX_PCT` fixed one column over: the field existed to be corrected rather than filled in, on a book where every line is entered as boxes x pcs/box and priced per 1000 pieces. Left on `unit`, `billedQty` reads the 120,000 pieces as 120,000 billing units and the line prices at **a thousand times** the intended money — wrong in the expensive direction, and invisible unless somebody checks the total. `Products.tsx`'s empty product takes the same default, so a product added to the catalogue starts there too; **no product already on file changes**, and picking one still adopts *its* unit, which is the more specific answer (`unit: p.unit` is untouched and `DEFAULT_UNIT` has exactly one use). A **default, not a rule** — the select is in the row, and a line stored on `unit` stays there. Measured in a harness: a fresh line opens on `per 1000`, and 10,000 pcs/box x 12 boxes at ₹10 comes out at ₹1,200.00 with ₹216.00 tax, which is the arithmetic the desk expects.
- **Line items are packaging-aware**: besides `qty × unit_price` (the billing basis — e.g. KGS × price/kg), items carry display-only `color`, `packs` (boxes/ctns), `pcs_per_pack`, `total_pcs`, plus `custom1..3`. The per-1000-pcs rate shown on PDFs is derived (`amount / total_pcs × 1000`), never stored. Picking a catalogue product fills `pcs_per_pack` from `products.pcs_per_pack`, so the packing defaults only have to be maintained in one place. A line may instead be a **charge** (`is_charge`) — freight, insurance, tooling — chosen as the third option in the editor's product select, since "which product?" and "is this goods at all?" are the same question. `billedQty()` short-circuits it to 1 so the unit price *is* the amount, `computeTotals` clears its packing/colour/loadability rather than storing figures the PDFs then hide, and every quantity column, quantity total and per-1000 rate skips it. It rides the whole chain (quotation → order → PI → invoice → packing list, including a quotation revision); the packing list keeps the row so its index still matches the invoice's, and simply does not print it.
- **Uploads arrive base64 in the JSON body** (logos, signatures, spreadsheets) — hence `express.json({ limit: '12mb' })` in `index.ts`; base64 inflates a file by a third. There is no multipart handling anywhere, deliberately: no multer, no temp files.
- **Data scoping is cross-cutting**: `server/src/middleware/scope.ts` (`scopeClause`, `canAccessCustomer`) must be applied in every list/detail/mutation route for customers, documents, follow-ups and the dashboard. Out-of-scope ids return 404, never 403, so employees can't probe for other owners' records. **`customer_id` is not the only id that needs checking.** A document body also carries `pi_id`/`order_id`/`quotation_id`, and an unchecked link is not a lesser hole: pointing an invoice at another owner's proforma returned that proforma's payment records — amount, date, method, bank reference — through the invoice's own response, and re-allocated its advances away from the invoice that had earned them. `linkError()` covers it, and requires the linked document to belong to the **same customer**, not merely to be visible: the carry-forward chain runs through one customer, and anything else corrupts every figure derived along it. `customerChangeError()` covers the matching hazard on every PUT — each one checked the row it was editing and then wrote whatever `customer_id` the body carried, so a document could be pushed onto a customer the caller does not own and could no longer see to undo.
- **The customer page is the one screen that reads across the whole chain** (`services/customerSummary.ts`, `GET /api/customers/:id/summary`, `pages/CustomerDetail.tsx`). Every document in this app hangs off `customer_id` and there was no way to ask the obvious question about one — what have we quoted them, what have they ordered, what do they owe — without opening five lists and filtering each by hand. Four rules hold it up. **A section the caller may not read is absent, not empty**: the map is assembled against `allows()` on the server, so the client renders what it was handed rather than filtering by `useCan()` — a copy of the access table on the client is a second policy, and it drifts. It is also what closes the leak this route would otherwise be: Production and Quality hold `customer: view` and `quotation: none`, and a page mounted on the customer function must not carry a price. Measured on a scratch instance across all five logins — the Super Admin gets nine sections, Logistics three (invoices, money, orders — its own matrix row), Production and Quality **only `qc`**, and Sales 404 on a customer it does not own. **Nothing here is a second opinion about money.** `invoiceReceivable` and `proformaAdvance` are asked rather than a balance re-derived, so the page and the invoice cannot disagree; verified against the document itself, €14,108.00 due on both. The money table is **per currency and never summed**, the rule `receivables.ts` states. **`advance_held` is what no invoice has absorbed** — what the proformas hold, less what the invoices raised from them have been credited with — and it is deliberately *outside* `received`, or the same money would be stated twice. Measured: a €20,000 advance against a proforma whose only invoice still owed €14,108 leaves outstanding 0, received equal to the invoiced total, and **€5,892 held**. **The currency mismatch is measured over the payments, not merged out of the per-document reports**: an advance is reported by `proformaAdvance` *and* by `invoiceReceivable` for every invoice raised from that proforma, so merging would count one wrong payment once per invoice. There is a test with two invoices on one proforma asserting it is reported once. The dialog moved to `components/CustomerDialog.tsx` when the list stopped being the only place to edit from — two copies of an eighteen-field form is how the two come to ask different things — and the list's name column now opens the customer rather than the edit dialog, since the usual reason to click a customer is to see what is going on with them. Each section shows the newest six and says how many there are, because six rows out of forty is a sample and a card that does not say so reads as the whole file.
- **The audit trail is captured once, above the routers** (`middleware/audit.ts` + `services/audit.ts`, read through `routes/audit.ts`). Thirty-odd routes mutate something, and a trail assembled by adding a call to each is a trail with holes — worse than none, because a gap looks exactly like "nothing happened". So the middleware works from the shape every route already has: an entity in the path, an id where there is one, a row underneath. It reads the row **before** the handler and again **after** the response and records the difference, so a route added later is covered the day it is added. Five rules hold it up. **It is append-only** — no route writes, updates or deletes an entry. **It records the change, not the request**: "grand_total 3,000 → 4,500", and a save that moved nothing writes nothing, though a *named* action (approve, status, a QC check) is recorded even with an empty diff because the act is the event. **It never reads `req.body`**, which is what makes "a password cannot reach the log" structural rather than a promise — the capture path only ever sees database rows. Sign-in is therefore the one thing recorded explicitly, by `routes/auth.ts`, naming just the address tried; `login_failed` is recorded too, being the entry somebody would actually come looking for. **A secret's *change* is recorded, its value never**: `password_hash` is reported as changed with no value, because that a manager reset an account is exactly what the trail is for — dropping the field outright was the first attempt and made such a reset produce no entry at all, the hash and `token_version` being the only columns it touches. Base64 images, JSON blobs and anything over 300 characters get the same treatment. **It cannot fail a save**: recording happens after the response, so a defect here loses an entry, never an invoice. Three traps found by the tests and worth not re-finding. **A delete's response id is not a create's** — `DELETE /work-orders/qc-checks/1` returns a body carrying `id: 1`, which was read as a newly created work order 1 and logged the whole job as though it had just appeared; the response is now consulted only when the action is `create`, and the handful of `/<entity>/<sub-resource>/<id>` routes resolve their real parent through `SUB_PARENT`. **`/api/settings` does not edit a table called `settings`** — it is the view of the default *company*, so entries are rewritten onto that company, where the Companies page would also look. **Line items live in a child table**, so the snapshot carries them as one synthetic `items` field, rendered **without row ids** — every save deletes and reinserts the lines, so comparing ids made re-saving an untouched document report that its lines had changed. Reading: `GET /api/audit` is the whole log and manager-only; `GET /api/audit/:entity/:id` follows the record, so whoever may open the quotation may read its history, resolved through `OWNER_SQL` — an entity missing from that map is refused outright rather than defaulting to visible. Timestamps are `datetime('now')`, which is **UTC**: `fmtDateTime` adds the Z before formatting (read as local it lands 5½ hours out on this desk, measured), and the Activity page converts its local date filters to UTC bounds for the same reason. The log costs about **440 bytes an entry** — roughly 2 MB a year at Aglo's volume — so there is no retention policy and does not need one. It starts empty: nothing before it shipped is in it, and both the Activity page and the History panel say so rather than implying a quiet history.
- **Pagination is opt-in** (`services/pagination.ts`, `listBody`). A list endpoint given neither `page` nor `limit` returns the whole thing as a bare array, exactly as it always did; given either, it returns `{rows, total, page, pages, limit}`. That is the contract, not a migration step: half these endpoints are also **pickers** — the customer select on a new enquiry, the product select in the line editor, the supplier list on a purchase order — and one that always paged would hand a select box the first fifty customers with nothing to say it had done so. Three rules the helper enforces so no route has to remember them. **The count is the list's own query wrapped whole** (`SELECT COUNT(*) FROM (…)`) rather than a hand-written `COUNT(*)` beside it, which cannot drift and copes with the two bodies that are not a plain SELECT — approvals is a `UNION ALL` of three tables, `orderLines` opens with a window-function CTE. **`order` must be a total ordering**: where the sort key has ties, which row lands on which page is undefined, so every one now ends in an id (four sorted on a name, a due date or a document date alone — the catalogue being the sharpest case, since a product is identified by name *and* colour *and* pcs/box). SQLite does not in fact shuffle them today, so that is a guarantee made explicit rather than a bug fixed; an added index would be enough to change the plan and the luck with it. **A page past the end is clamped to the last one** and the response says which page it served, because an empty table reads as a fault rather than as an absence. The per-row decoration those lists do (`dispatchProgress`, `progressForMany`) now runs on the page's rows, so the N+1 they always had is bounded by the page size instead of by how long the business has been trading. Two lists print a figure over their rows — despatches' pieces/boxes/unbilled and work orders' jobs/planned/made — and those come back as a `summary` measured over the **whole filtered set**, because a page total wearing the words of a list total is worse than no total. `/orders/by-product` is deliberately **not** paged: it folds every matching line into one row per product, and it is bounded by the catalogue rather than by trading volume. The masters (locations, suppliers, transporters, materials, machines, moulds) are not paged either, for the same reason. Client side, `lib/usePagedList.ts` owns it: the page lives in the URL like the filters, the previous page stays on screen while the next loads, and **changing anything else about the list returns you to page 1** — driven off the query key changing, so it covers filters held in plain component state too, and applied during the same render so the discarded page is never fetched.
- **Exporting a list is one writer** (`services/xlsx.ts`, `buildXlsx`), the counterpart to the reader in `spreadsheet.ts` and dependency-free for the same reasons — an .xlsx is a ZIP of XML parts and Node ships both halves in `node:zlib`. Scope is narrow on purpose: one sheet, a bold frozen header with an autofilter, and four cell kinds (text, number, money, date). The rule that matters is that **numbers are written as numbers and dates as real dates**: a quantity that lands in Excel as the string "21,00,000" cannot be summed, which is the one way an export can be useless while looking correct. Grouping is left to Excel's own locale, which renders `2100000` as `21,00,000` on this desk without anything being baked into the file. Three traps worth not re-finding. **Column widths are sized to what Excel draws, not to the raw string** — `String(12600000).length` is 10, the cell renders `1,26,00,000.00` at 14, and the column showed `########`; `displayWidth()` counts separators the Indian way, the wider convention being the safe one to size against. **Control characters are stripped**, because one makes Excel declare the whole workbook corrupt with nothing to say which cell did it. And the **ZIP timestamp is fixed rather than taken from the clock**, so the same input gives byte-identical output and the writer can be tested at all. `/api/orders/export?view=lines|by-product|orders`, `/api/quotations/export`, `/api/proformas/export` and `/api/invoices/export` are the callers, each declared **above `/:id`** or Express reads "export" as a document id; each list's WHERE is built by a named `…ListWhere(req)` shared with the list itself, so the download cannot drift from the table above it. The invoice export decorates each row by **asking** `invoiceReceivable` rather than re-deriving a balance, and carries the currency-mismatch figure in its own column, because an advance that is silently uncounted is exactly what somebody would open a spreadsheet to find. The client's `DownloadButton` in `components/ui.tsx` is an anchor, not a fetch: the session is a cookie on this origin, so nothing has to be held in memory as a blob. Each export it exports the **whole filtered set, never a page** (`page`/`limit` are ignored), goes through the same `lineFilters`/`orderListWhere` as the view it came from so the download matches the screen, and is scoped by `scopeClause` like every other read. Verified by reading the output back with the project's own reader — the two share no code — and by opening it in Excel itself over COM, which is the only thing that can prove Excel does not offer to repair it.
- **The three registers export too** — despatches, the QC register and payments — and each is the same four moves: a named `…Where(req)` shared with the list so the download cannot drift from the table above it, a route declared **above `/:id`** (Express reads "export" as an id otherwise), the whole filtered set rather than a page, and the mount's own guard. That last is not automatic: `qc-checks/export` carries `requirePermission('qc')` explicitly, because a read mounted without its own guard is how a whole list escapes through a route nobody thinks of as part of the module — the trap `routes/pdf.ts` records about the purchase order. Measured across all five logins, the three answer exactly what the access matrix says: despatches 200 for Logistics and 403 for Sales, QC 200 for Production and Quality and 403 for Logistics, payments 200 for Sales and 403 for the three factory teams. Despatch pieces and boxes are summed **in SQL** rather than by loading each trip's lines — the list does the latter only because it shows them. The QC file writes the **verdict as a word** (Pass, Fail, *Not measured*), since that is what somebody reconciling filters on, and it keeps visible the one distinction that matters: nothing measured is not a pass. Verified by reading all three back with `spreadsheet.ts`, which shares no code with the writer — dates come back as serials, so they were written as real dates rather than text; every filter narrows the file exactly as it narrows the screen; and a Sales download of the payments register contains neither the admin's customer nor a bank reference **in its bytes**, not merely in its row count. Writing it found one quiet defect: the despatch columns named a `remarks` field that does not exist — the column is `notes` — which would have shipped a permanently blank column rather than failing.
**`npm run check-series`** (`src/db/checkSeries.ts`) audits what was saved before the guard existed: it rebuilds each company's patterns as regexes and reports any order, proforma or invoice whose number came from the *other* series. Read-only, opened read-only, and deliberately with no `--fix` — which of the two halves is wrong is a judgement (the number may already be on paper with a customer), not a migration. A number matching neither pattern is reported separately rather than as a fault, since the Number field is editable by hand and `AGLO/EX/25-26/118A` is a real Aglo document. Writing it found that the **seed** had the same defect from the other direction, calling `nextNumber('proforma', …)` without `isExport` and then inserting `is_export = 1`. - **Each company numbers in its own name, and that was the missing half of per-company numbering.** The counters were always right: `sequences` is keyed `(company_id, doc_type, year)`, every entity starts at 001, and the unique indexes are per company precisely so that two of them may both hold a 001. What did not follow was the **pattern**. A company created through `POST /api/companies` took the `companies` table's column defaults, which are *Aglo's own paperwork* — `AGLO/PI/{FY}/{SEQ}`, `AP/{SEQ4}/{FY}` — so the second entity's first proforma printed `AGLO/PI/26-27/001`, character for character the first entity's number, with another company's name in it. Nothing refused it and nothing could. Measured before the fix on a scratch instance: two companies, two proformas, the identical `AGLO/PI/26-27/001`; two invoices, the identical `AP/0001/26-27`. **The restart was working perfectly and was invisible**, which is the worst way for it to work. So `services/companyPatterns.ts` derives a new company's ten patterns from its own name, and the derivation is checked against the only real patterns anybody has: *Aglo Polymers Pvt Ltd* gives slug **AGLO** and initials **AP**, which is exactly how Aglo's documents are numbered. That is the evidence it follows the convention on this desk rather than inventing one — first word for a long series, initials for the invoice — and it is asserted in the tests. The file is **pure, with no `db` import**, because `db/connection.ts` needs it for a boot migration and `services/numbering.ts` imports `db` from that file; putting it there would close the circle `documentChain.ts` already has to work around. Two smaller things went with it. **`wo_pattern` and `po_pattern` were missing from the companies route's `FIELDS`**, so those two series could not be set on creation or edited afterwards and every entity in the group issued `WO/26-27/001`; the list is now `PATTERN_COLUMNS` itself, and Settings gained the two fields. And **Settings warns when another company holds the same pattern**, reading the form's live values against what the others have saved, so it answers while a pattern is being typed — a derivation cannot help two companies that genuinely read the same (*Aglo Polymers* and *Aglo Packaging* both give AGLO), and a shared pattern is invisible on the document itself.
- **The backfill for companies already on file is deliberately timid.** A pattern that has issued a number must never be rewritten — that number may already be on paper with a customer — so the migration in `connection.ts` moves a non-default company only when **every** pattern column is still *exactly* the schema default (so one somebody configured is left alone, including one configured to match, which is then their choice) **and** it has no row in `sequences` at all, in any fiscal year, so nothing has ever been drawn from any of its series. It is idempotent by construction: after the rewrite the patterns are no longer the defaults. Verified on a scratch instance planted with four companies — the default untouched; an unconfigured, unused second company moved to `SECOND/PI/{FY}/{SEQ}` and `SE/{SEQ4}/{FY}`; a third holding the defaults but with one proforma number issued **left alone**; a fourth with a hand-set `pi_pattern` left alone entirely; and a second boot moved nothing. The two left alone are exactly what the Settings warning is for, and it named them, listing nine and ten shared series apiece and dropping a row the moment the field was typed into. The **`SCHEMA_DEFAULT_PATTERNS` copy is what decides "never configured"**, so a test reads `schema.sql` and asserts the two still agree: if the schema moved and this copy did not, the comparison would quietly stop matching and the migration would do nothing while looking like success.
- **The type is not asked twice.** `NewDocumentDialog` asks export or domestic before anything else and then lists **only that kind of customer**, so the Type control the form then showed was a second answer to a settled question — and answering it differently left a domestic customer on an export document, which is the one thing the dialog exists to prevent. On a **new** quotation, proforma and invoice the control is gone and `SettledDocumentType` states the type instead — **as a badge and nothing else**. The explanatory sentence is rendered only once a number exists: then the flag really is frozen and somebody looking for the missing control needs telling why, whereas on a new document the dialog has just asked and a sentence explaining the answer back to the person who gave it is noise. The reason stays on hover. **A saved quotation keeps its picker**, deliberately: `patternColumn` gives quotations one series whatever their type, so nothing can disagree and guarding it would take away something safe — the same reason `exportChangeError` skips them. Proformas and invoices were already settled once saved. **Removing the control exposed a real bug it had been masking**, which is why the derivation had to be fixed first: arriving from an **enquiry** carries a customer but no `type`, and the effect that reads the customer only ever adopted the currency — so an overseas buyer got a domestic quotation with IGST on it and nothing said so, the Type dropdown being the only way to notice. `fromCustomer()` is now one derivation used both by the customer picker and by the arrive-with-a-customer path, so the two cannot disagree. Verified in a harness on the real route table: a new quotation shows no picker and reads *Domestic*, a saved one still offers the picker, an enquiry for a German customer opens as **Export, EUR, no tax** where it used to open domestic, and the proforma and invoice tick-boxes are gone in favour of the same statement.
- **A document's export/domestic flag is fixed once it has a number** (`exportChangeError` in `services/numbering.ts`, guarding the PUT on orders, proformas and invoices). The number is drawn from the export or the domestic series at creation and is never reissued — deliberately, since it may already be on paper with a customer — so flipping the flag afterwards could only ever leave the two disagreeing. The forms allowed exactly that, silently: an export proforma created as `AGLO/EX/26-27/001` came back from a PUT as `is_export = 0`, `tax_type = igst`, a domestic document holding an export number and charging GST. Same shape as `customerChangeError`, and there for the same reason — the PUT wrote whatever the body carried. **Quotations are deliberately not guarded**: `patternColumn` gives them one series whatever their type, so nothing can disagree and the type stays editable; guarding it would take away something safe. Packing lists and work orders likewise. Client side the control is editable only while `isNew` — after that `SettledDocumentType` in `components/ui.tsx` states the type and why it is settled, so the server's 409 is never a surprise.
- **Text search is one helper** (`services/search.ts`, `searchClause`), shared by the quotations, proformas and invoices lists and shaped like `scopeClause` — it returns `{sql, params}` for the route to push onto its own WHERE rather than owning the query, because every other filter is built that way and the one that was not would be the one that drifted. All three search **number or customer name**, matched as a substring, so `003` finds `QT/26-27/003` without typing the series out. It is **server-side, and must stay that way**: these lists are paged, so filtering the rows already fetched would search only the current page. Two things the helper exists to get right. **`%` and `_` are LIKE's own wildcards** — typing either matched every row instead of the character, so the term is escaped and every LIKE carries its own `ESCAPE` clause (SQLite does not carry one across an `OR`); parameters were always bound, so injection was never the concern, and Aglo's numbers and names contain neither character today, which makes this correctness ahead of need rather than a fix to anything observed. **The clause is parenthesised**, because `scope AND a LIKE ? OR b LIKE ?` binds as `(scope AND a) OR b` and the search would then be a way straight past data scoping — there is a test asserting the brackets for exactly that reason. `routes/customers.ts` and `routes/products.ts` have their own older inline searches and still behave the unescaped way. Client side each page holds the term in the URL through `useUrlFilter('q')` and puts it in the query key, so typing returns to page 1; the empty state reads *Nothing matches those filters* when any filter is set, rather than claiming the book is empty.
- **The order book is read three ways over one search box, so the term means one thing in all three** (`orderSearchClause` in `services/orderLines.ts`). It did not: the lines and by-product views searched the item's description, code and colour, the per-order list took no term at all, and the client dealt with that by **hiding the box on that tab** — so something typed on one view silently stopped applying when you switched to another. The rule is now one function with two shapes, because the two callers need different SQL for it: given a line alias the item columns are matched directly, and without one they become `EXISTS (SELECT 1 FROM order_items …)`, which is the same question put to a row that is one order rather than one line. Six columns — our own number, the customer's PO number, the customer's name, and the item's description, code and colour — which is what somebody at this desk actually has in hand. A test runs **both shapes over the same fixtures and asserts they return the same orders** for each of the six, the precedent being `qcRegister.test.ts` doing that for `resultOk` and its SQL twin; measured live as well, on all three views plus both exports. Two consequences worth keeping. It is **server-side** because these lists are paged, so filtering the rows already fetched would search the page in hand rather than the book. And it goes through `searchClause`, so `%` and `_` are escaped — with a real order on file called *50% Recycled Handle* and a code `PRF_28`, `q=50%` finds the one and `q=PRF128` finds neither, where unescaped both terms returned everything. `routes/customers.ts` and `routes/products.ts` moved onto the same helper at the same time; their hand-written clauses were **already bracketed** — which mattered, `scopeClause` sharing that WHERE — so what changed there is the escaping alone. The bracket is what keeps a search from being a way past data scoping, and it was measured rather than assumed: an order booked for a customer Sales does not own is invisible to Sales under every term that finds it as the Super Admin, `%` included, in the list, the lines view and the spreadsheet export.

The **columns stay and the draft still round-trips every one**, the rule the header freight fields follow: an order raised before this keeps what it holds, an ordinary save cannot zero it, and the order PDF, the spreadsheet export and the order book still print what is there. What is gone is the only way to type a new one, and **three figures go quiet with it on orders raised from here on**: the dashboard's *overdue orders* counts orders past `promised_date`, and `orderLines.ts` reads the same header column for the Promised column and for `next_due` — none of them falls back to the per-line date. That was stated before the removal and chosen anyway; the cheap repair, if those figures are missed, is for both readers to fall back to the earliest `order_items.scheduled_date`. **Per-line Promised is untouched** and is the reason this is survivable: it is a column in the item editor and prints on the order PDF, so a date per line is still recorded — and Destination and Transport are recorded per trip in the despatch register, which is the record the lorry actually leaves against. **INCO Terms and Containers moved to Details rather than going with it**: they were in that card but are export-only, hidden on the domestic order this was asked about, and every other form keeps its INCO field in Details. Verified in a harness on the real route table: the card is gone on both types, an export order shows INCO Terms and Containers in Details, and saving an order that predates the change sends all seven stored values back unchanged.
- **A line has its own promised date, and its despatch date is derived** (`ORDER_ONLY_COLUMNS` in `components/ColumnsControl.tsx`). `order_items.scheduled_date` and `dispatched_date` have been in the schema and round-tripped through `saveItems` since the order book was written, and `LineItemsEditor` never drew either — columns the API carried that nothing could type into. Lines on one order genuinely fall due on different dates, which is what the desk sheet has a column for, so **Promised** is now an ordinary toggleable column in the extras row and prints on the order PDF beside Code and Supplier. **Despatched is deliberately not the stored column.** It is read from the despatch register — `despatchedByOrder` gained `MAX(d.date)`, MAX rather than MIN because a line shipped over three trips is best described by the most recent — and rendered read-only, because a date somebody types can contradict the lorry, which is exactly the failure `services/orderLines.ts` describes on the real sheet: rows still marked Pending that the Despatch sheet shows went out. `order_items.dispatched_date` keeps round-tripping untouched rather than being repurposed, so nothing already stored is at risk. Writing it turned up a **pre-existing silent drop**: `code` and `supplier` exist on `order_items` alone, but sat in the shared `ITEM_COLUMNS` with no omission, so a quotation, proforma or invoice offered both in the tick-list, drew a box for each, and the INSERT threw the value away without a word. Measured before the fix — a quotation line sent with `code: 'PRF-28-SPEC'` came back `code: null` while the same line on an order kept it. They join `ORDER_ONLY_COLUMNS`, which goes into `QUOTATION_OMIT`, `PROFORMA_OMIT` and a new `INVOICE_OMIT` (the invoice had no omit list at all and its editor was never passed one) — an **omit** rather than a `FORCED` entry, because this is the "never has this column" case that file already distinguishes: the document has nowhere to put the value, so the editor must not invite one. The PDF half is tested both ways: an order using per-line dates prints the column, and one that does not **has no such column at all**, `itemsTable` dropping a column with no data anywhere — which is what makes this safe for every order already on file.
- **Columns are per-document**: `column_config` JSON (`{hidden:[], custom:[]}`) drives both `LineItemsEditor` and the PDF. PDFs build their items table from a `ColumnSpec[]` passed to `itemsTable()` in `services/pdf.ts` — a column with no data anywhere auto-hides unless marked `always`. Add new columns to the spec list, never with ad-hoc `if (hasX)` branches. A spec may carry a `sum`, which adds that column up in a closing **TOTAL** row — only for genuinely additive figures (boxes, pieces, money), never a rate or a pcs-per-box, where the total would look authoritative and mean nothing. **Total Qty is only additive within one rate basis** — the column reads in whatever the line is priced against, so `qtyTotal()` buckets by basis and prints one labelled figure per bucket (pieces bare when they are the only basis). Adding pieces to tonnes produced `30,50,005`, a number true of nothing. Charge lines are excluded outright (`goodsOnly`); a freight line raised *before* `is_charge` existed is still just a per-unit line and still contributes its 1, which is why the per-1000 rate also keeps its "at least a thousand pieces" guard. `itemsTable` also takes the document's money rows as a `footer`, so freight, tax and the grand total can sit *inside* the table instead of in `totalsBand` beside it. **The proforma and the commercial invoice both do this**, and it is worth about 27pt on the invoice — a third of an inch, measured — because a band row carries four points of padding top and bottom plus a rule, and each band block carried its own margin as well. The invoice folds its payment lines in too, so Amount Received and Balance Due stop being a second floating block. Where the sums live is stated rather than positional: a `MoneyRow` marked `sums` carries the column totals, defaulting to the last row. That marker exists because the invoice puts payment rows *after* the grand total, and the boxes shipped have nothing to do with the balance outstanding. The invoice **keeps its subtotal** where the proforma drops it — CGST and SGST are charged on the taxable value, and the figure they are charged on has to be legible. **The table closes on exactly one row**: the sums ride on the last money row (the grand total) rather than getting a TOTAL row of their own, and the proforma drops the subtotal line entirely, so the final column shows the grand total — freight included — not the sum of the amounts above it. The freight line sits directly above carrying its own value, which is what keeps the addition checkable. A spec may also carry a `group`, which draws a banner across the adjacent columns sharing that name (the proforma's **QUANTITY** over CTN./IMAGE/PCS. per CTN., copied from the AGLOPACK proforma); the banner shrinks with its run when a member auto-hides, and a table with no groups keeps its single header row. On top of that, each document type **omits** the columns it never carries — `quotationOmit`/`proformaOmit` in `components/ColumnsControl.tsx`, mirrored by the PDF spec. Neither the quotation nor the proforma shows a **per-line HSN** (Aglo's own documents put the HS code once in the proforma's customs header; the commercial invoice is the one that prints it per line), but both keep *storing* it so it reaches the invoice down the chain. Both also drop **Qty**: one quantity per line, never two that can disagree. That makes **Total Qty the billing quantity, read in whatever the rate basis is** — pieces against a per-1000 rate, kilos against a per-kg one — so `billedQty()` in `services/totals.ts` falls back to `total_pcs` when there is no `qty`. That fallback is strictly additive: it only fires where the answer used to be null, so no document already raised changes its amount (there is a 128-combination check for exactly this). Its corollary is that the proforma's rate column is **per 1000 pieces** (`amount / total_pcs × 1000`, derived from the line's own money so a per-piece rate converts up rather than being restated) and only when `isPieceBasis()` — money ÷ kilos is not a piece rate, and a wholly weight-billed proforma relabels the column `Price <cur>` rather than lying. Per *single* piece was tried and reverted: at Aglo's prices it rounds to nothing, printing ₹0.01 where the per-1000 rate reads 10. Orders and commercial invoices keep Qty, so a weight-billed invoice still states its KGS. Container loadability (`qty_20ft`/`qty_40ft`) is export-only on quotations and proformas. Both are **default-hidden on a new document** (`DEFAULT_HIDDEN_COLUMNS` in `components/ColumnsControl.tsx`): loadability answers "how many boxes fill a container", which the Container Planner and the proforma's Container Fitment panel already answer, and which clutters every line the rest of the time. It is a **default, not a rule** — `newColumnConfig()` writes it into the document's own `column_config` at creation, so the choice is stored with the document, a document already raised keeps whatever it was saved with, and changing the list later reformats nothing on file. Carry-forward only copies the source's columns when `hasColumnPrefs()` says it has some, or a quotation saved before the defaults existed would hand a blank config to the proforma and undo them.
- **Some columns a document type shows whatever its config says** (`PROFORMA_FORCED`/`INVOICE_FORCED`/`ORDER_FORCED` in `components/ColumnsControl.tsx`, `forceColumns()` in `services/pdf.ts` — one list kept on both sides, or the paper and the screen disagree about the same document). Taking a column out of the tick-list only stops it being turned off *there*, and a config is not written there alone: **carry-forward copies the source's hidden columns onto the new document**. A quotation sent as a rate-and-packing price list carries `amount` hidden, and that landed on the proforma raised from it — where there is no tick to bring it back — then rode on to the order and the commercial invoice, which cannot be presented for GST or customs with no amounts at all. Measured on a scratch instance, the same four documents before and after: the proforma printed `SL No. · DESCRIPTION · COLOR · QUANTITY · USD/1000 Pcs` and now prints `… · TOTAL QTY · USD/1000 Pcs · TOTAL AMOUNT (USD)`; the order and the invoice each gained their Amount column; **the quotation is byte-identical**, because the price list is the one document allowed to drop them. `total_pcs` is forced on the **proforma only**: `qty` is omitted there, which leaves Total Qty as its only quantity column, so hidden it cannot say how much of what is being bought — and the amount it inherits reads blank because nothing can be typed to produce one. Orders and invoices keep Qty and so do not need it. The rule is applied **where the columns are drawn, not where they are chosen**, so a document already saved with such a config repairs itself on the next read and there is nothing to migrate.
- Quotation **revisions**: same `number`, incremented `revision`; old row gets `superseded_by` pointing at the new one and becomes read-only in the UI. List views hide superseded rows unless `?all=1`.
- **Duplicating a quotation is not revising it, and the number is the difference.** A revision is the next round of one negotiation — same number, `revision+1`, the old row superseded. `POST /quotations/:id/duplicate` is a *separate offer* that starts from this one: its own number from the series, nothing superseded, the source untouched. Re-quoting last season's prices and quoting a second customer the same basket are both this. Four things deliberately do not carry across, and each has a reason worth keeping. **`enquiry_id`** — `quotation_count` counts unsuperseded quotations against an enquiry, so carrying it would report two answers to one question, which is the exact thing that count exists not to say (a revision carries it for the opposite reason: it *is* the same answer). **The approval** — the copy starts `draft`/`not_submitted`, because approval attaches to a document somebody read, and copying it would be an automatic path from nothing to approved. **`internal_notes`** — the usual reason to duplicate is to quote somebody else, and the customer is editable afterwards, so carrying the running commentary is how one customer's private notes reach another customer's file. **A validity date already past** — copied as-is it yields an offer that lapses the moment it is sent; it survives as a *draft* (only `sent`/`negotiating` lapse), which makes it worse rather than better, because the trap springs later. Line items and totals *are* copied verbatim: they are the source's own server-computed figures and nothing about them changed.
- **The quotations list hides `rejected` by default** (`HIDDEN_BY_DEFAULT` in `routes/quotations.ts`), and `status` takes a **comma-separated list** rather than one value. Both came from the client: a price somebody turned down is not work, and "sent or negotiating" is not a question a single `<select>` can ask. Three rules. The default applies **only when nothing was asked for** — naming any status shows exactly what was named, and `status=all` shows everything. What it hides is **a decision somebody made, never a date that passed**: `expired` is deliberately still shown, because a lapsed offer is revived by extending its validity, which is a job still to do and the whole reason `quotationExpiry.ts` can move a quotation back. There is no `lost` status to hide either — the CHECK constraint has six values and `rejected` is what "lost" means here. And it **must be server-side**: the list is paged, so dropping rows on screen would only ever drop them from the page in hand. The export shares `quotationListWhere`, so a download can never hold rows the table above it did not. Client side `MultiSelectFilter` in `components/ui.tsx` owns the control; an empty value is **not** "nothing selected" but "this list's default", so the closed box names that default rather than sitting blank, and ticking every option is written to the URL as `all`.
- **Payments** (`payments` table) link to *either* a PI (`pi_id`, advance) or an invoice (`invoice_id`). **`services/receivables.ts` owns the "how much has this invoice been credited" rule** and is the only place that may answer it: a payment on an invoice belongs to that invoice, while a PI advance is a pool **allocated across the invoices raised from that PI** (earliest first, capped at each invoice's remaining balance) because partial shipments are normal. Counting the whole advance against every invoice credits the customer several times over. **Money only adds up within one currency** (`sameCurrency`): a payment credits a document only when the two agree, because a €10,000 advance is not ₹10,000 and treating it as one once marked a ₹5,000 invoice paid in full. There is no rate stored anywhere and inventing one would put a fiction on a ledger, so a mismatched payment is **not** allocated and **not** converted — it comes back as `currency_mismatch` and the invoice page says so, since silently under-reporting is the one outcome worse than an awkward figure. A blank currency counts as matching: payments inherit their currency from the document (`routes/payments.ts`), so an empty one can only be a legacy row, and excluding it would quietly reduce a balance that has been right for months. The rule is applied identically in `invoiceReceivable` and `receivedByInvoice`, or the dashboard and the invoice page disagree. `routes/invoices.ts` `getFull`, `routes/dashboard.ts` receivables and `services/pdf.ts` `buildInvoicePdf` all call it — never recompute payment totals inline. The allocation is derived on read, never stored.
- **Money in has a register of its own** (`GET /api/payments`, `pages/Payments.tsx`). `routes/payments.ts` was a POST and a DELETE and nothing else, so a payment could only ever be seen on the one document it was banked against — *what came in this week* and *which of these is credited to nothing* had no answer outside the dashboard's Cash Collected bar. Filterable by date range, customer, method, and by whether it is an **advance** (against a proforma) or a **settlement** (against an invoice), which are different things to look at; searchable through `searchClause` over the bank reference first, since *did we get SWIFT REF 8842544* is the lookup it will actually be opened for. It is deliberately **not an allocation report** — where an advance ends up is `receivables.ts`'s question, answered on the invoice and on the customer's page, and a second opinion about it here is the one thing this must not grow into. The summary is over the **whole filtered set** and is **per currency, never one total**, the rule that file states; verified that `?limit=1` still counts every row. **The mismatch filter is the reason it exists**: money in a currency its document is not billed in is allocated to nothing, and until now that was reported one document at a time, so nobody could ask how many there were. Answering it over a paged list needs the rule in SQL, so `currencyMismatchSql` sits beside `sameCurrency` in `receivables.ts` and `paymentsRegister.test.ts` runs both over all 49 combinations of blank, padded and differing currency asserting they agree — the exception `RESULT_FAILED_SQL` already established, and the price of taking it. Measured on a scratch instance: a ₹111 payment on a € invoice is listed, flagged *not EUR*, counted in `mismatched`, kept out of the EUR total and found by `?mismatched=1`. Logistics, Production and Quality answer **403** — they hold `payment: none` — and scoping holds for Sales under every term including `%`.
- **The proforma PDF states the advance, because that is the document the advance is paid against.** It printed subtotal, tax and grand total and nothing about money already banked — so a proforma sent after a part payment asked for the whole sum a second time. `Advance Received` and `Balance Payable` now close the items table, in the shape `buildInvoicePdf` already used, and **only when there is an advance**: a proforma nobody has paid against prints exactly what it always did. Two things it has to get right. `sums: true` stays on the **grand total** rather than defaulting to the last row, or the boxes-and-pieces totals would slide onto Balance Payable — the invoice's own reason, that what is still owed is not a property of what is being shipped, and there is a test asserting the middle columns of each row. And the figure is asked of `services/receivables.ts` (`proformaAdvance`) rather than re-derived: the currency rule already lived in two places with a stated invariant that they agree, and a third copy in the PDF is exactly how the paper and the screen come to disagree — `routes/proformas.ts` `getFull` now calls it too, leaving the list's correlated subquery as the only other implementation, which is deliberate and documented (asking once per row is the N+1 this codebase keeps bounding). Measured on the seeded export proforma: **€33,845.00 total, €10,153.50 advance, €23,691.50 balance**, matching what the page reports to the paisa. A payment in another currency is still credited to nothing and reported instead — there is no rate stored anywhere, and inventing one would put a fiction on the document.
- **And the commercial invoice adjusts for that same advance by name.** `invoiceReceivable` has credited this invoice's share of the proforma's advance since it was written, so the balance was never wrong — but the document printed one **Amount Received** line, which left the buyer no way to see that the money they paid against the proforma had been set against this bill. It now reads *Advance Received (AGLO/EX/26-27/001)* · *Amount Received* · *Balance Due*, so the two documents can be read together: the proforma states the advance, the invoice deducts it under the same words. Three rules, each about saying nothing rather than saying zero. It **names the proforma**, because an advance is banked against *a* proforma and a buyer may hold several — the number comes from the row already fetched for the reference cell. An invoice settled entirely by advance shows **no Amount Received line at all** rather than a zero, and an invoice with **no advance prints exactly what it always did** — one line, no mention of a proforma — which is what protects every invoice already raised; there is a test for that half specifically. And an advance in another currency is still credited to nothing and adjusted for by nothing, the rule `receivables.ts` owns. The figure is `advance_applied`, **asked** of that service rather than re-derived, so the paper, the page and the spreadsheet export (which has carried an *Of which advance* column all along) cannot disagree. The subtlety `proformaAdvance` records applies here too: inserting a row between the grand total and the balance is exactly the change that would slide the column totals down onto it, so `sums: true` stays on the grand total and the test asserts the payment rows carry a label and one figure and nothing else. The invoice page says it too — `PaymentsCard` takes an optional `advanceApplied` and shows *of which advance* beside Received, on the **invoice only**, since on a proforma every payment *is* the advance and the split would say nothing. Measured on the seeded export invoice: €34,261.50 total, €10,153.50 advance from the PI, €10,000.00 paid here, €14,108.00 due — the same four figures on the document, on the page and from `getFull`.
- **The proforma follows the same currency rule, and did not used to.** `routes/proformas.ts` `getFull` summed *every* payment on the PI whatever its currency, so a €10,000 advance and ₹10,000 added to 20,000 of nothing — the exact arithmetic `sameCurrency` exists to refuse. The list carries the advance too, as `advance_received`, computed by a **correlated subquery in `listSql` rather than a call per row**, since the list is paged and per-row would be the N+1 this codebase keeps bounding. Both ends apply one rule (blank currency matches; a differing one does not) so the list and the proforma page can never report different advances, and both surface what they excluded — `currency_mismatch_count` on the list, `currency_mismatch` on the document — because silently under-reporting what a customer has paid is worse than an awkward figure. **Balance is a subtraction, not a third opinion**: `grand_total − advance_received`, done where it is displayed, so `advance_received` stays the single source. Nothing changed in the local `server/data/app.db` when this landed: it had no payments recorded at all. **That database is not the one the business is using** — it holds 2 proformas where the deployed instance shows 7, so a claim about "the live book" made by reading it is a claim about a stale local copy.
- **Proformas gained `internal_notes`**, the field quotations have had from the beginning — so the team's commentary on a negotiation no longer stops at the moment it becomes a document. Additive, as every schema change must be (`schema.sql` plus `addColumnIfMissing`), defaulting to `''` so existing rows migrate silently. It is saved by `PATCH /proformas/:id/internal-notes`, deliberately **not** through the document's PUT: going that way would trip `resetApprovalOnEdit` and knock an approved proforma back to `not_submitted`, and rewrite every line item, over a sentence nobody outside the office reads. `components/InternalNotes.tsx` is now written against a **doc type** rather than a quotation id (`ENDPOINT` maps type → path and query keys), because a second near-identical copy of it is how the two would drift apart.
- **Duplicating a proforma** is the quotation rule plus one hazard of its own. **`order_id` must not carry across**: an order has no `pi_id`, so the link lives on this column and `dispatchProgress()` walks it — a copied link would point a second proforma at an order that already has one, exactly what `POST /orders` refuses from the other direction and for the same reason. **`quotation_id` does not carry either**: two proformas both claiming to be the one raised from a quotation makes "which document came from this quote" unanswerable, and `prefill/from-quotation/:id` remains the way to attach one properly. Payments are not copied (they are money received against *that* document), the approval resets, internal notes stay behind, and a validity date already past is dropped. The number comes from the source's own series — `is_export` is copied, so an export proforma duplicates into the export series.
- **The proforma's vocabulary is Draft → Sent → Order Confirmed → Advance Received → Sales Order Generated, with Cancelled and Expired off to the side** (confirmed with Aglo 2026-09-03), and the last two are again set by the code rather than by a person. `in_production` is relabelled **Sales Order Generated** and `syncProformaOrdered` now sets *it* when the order is booked, where it used to set `order_confirmed` — which said the wrong thing, since Order Confirmed is the buyer telling us to go ahead and comes *before* the advance is banked, while booking the order is the last step and ours. The guard widens to match (`draft`, `sent`, `order_confirmed`, `advance_received`), still forward-only and still never touching `cancelled`, measured both ways. **Expired is derived and never stored**, and that is the interesting difference from the quotation: `expired` is not one of the six values in this table's CHECK constraint, and SQLite cannot ALTER a CHECK, so storing it would mean rebuilding the table and copying every live row for what computes in five lines. Derived it also corrects itself — extend the validity and the proforma is simply live again, with no `status_before_*` column to keep honest. `STATUS_SQL` in `routes/proformas.ts` is that expression, and it is **selected after `p.*` so the later alias wins**, which is what lets one CASE cover the list, `getFull` and the spreadsheet export with no route mapping rows by hand; the list's status filter uses the same expression rather than `p.status`, since an alias cannot be referenced in WHERE and a status you can see but cannot filter for is a row you cannot find. Only `draft` and `sent` lapse — once the buyer has confirmed, paid or had an order booked, the validity date has nothing left to say — and a blank date never lapses. `date('now')` is UTC, so east of Greenwich it lapses up to 5½ hours **late**, which is the safe direction. Client side `pages/Proformas.tsx` owns the vocabulary the way `Orders.tsx` owns the order statuses. One collision checked rather than assumed: `in_production` is also an order and a work-order status, but neither renders through `StatusBadge` (both pages carry their own label maps), so the two readings never meet.
- **The quotation's status vocabulary is Draft → Negotiating → Proforma Generated, with Rejected and Expired off to the side** (confirmed with Aglo 2026-09-03) — and **only the first, second and Rejected are set by a person**. The other two are observations, so they are set by the code that observes them, the rule `orderStatus.ts` and `invoiceStatus.ts` already follow for their own fields: `accepted` by `syncQuotationConverted` when the proforma is raised, `expired` by `quotationExpiry.ts` when the validity date passes. Typed by hand, *Proforma Generated* would claim a document that does not exist, and *Expired* would be **permanent** — `status_before_expired` is filled only when that sweep expires it, so nothing could revive it. Killing a live offer early is `rejected`. `POST /quotations/:id/status` refuses the rest with **409** (a real status, just not one this route hands out), so it is a closed door rather than a hidden button. **The stored values do not change**, deliberately: SQLite cannot ALTER a CHECK constraint, so a rename means rebuilding the table and rewriting live rows — for wording — and these strings are load-bearing in `approval.ts`'s outgoing list, `quotationExpiry.ts`, `syncQuotationConverted`, the dashboard funnel and the list filters. The vocabulary is therefore a **display layer**: `accepted` is labelled *Proforma Generated* (in `StatusBadge` and in `pages/Quotations.tsx`, which owns the list the way `Orders.tsx` owns the order statuses), and `sent` is **retired, not removed** — no longer offered, since a quotation with the customer is being negotiated, but still labelled, coloured and filterable, because a status you cannot filter for is a row you cannot find. One consequence worth knowing: **→ Create Proforma** was gated on `status === 'accepted'`, which became a door locked from the inside once that status was what the button *sets* — it is now offered on anything not rejected, superseded or already converted, and the server settles a draft (a manager converting one approves it in the same action; an employee is told to submit it first).
- **A quotation lapses on its validity date** (`services/quotationExpiry.ts`). `expired` was a legal status from the first day and nothing ever set it, so a price offered in April still read *Sent* in September. This is `invoiceStatus.ts` applied to the calendar and borrows its shape: `syncQuotationExpiry(id)` runs after anything that touches a quotation, and `sweepQuotationExpiry()` runs on boot and daily, because a date passes whether or not anybody is logged in and the app may have been down over the day that mattered. **Only a live offer can lapse** — `sent` and `negotiating`, the two the dashboard has always counted. A `draft` was never offered so there is nothing to lapse, and `accepted`/`rejected` are decisions somebody made, never touched, the rule `orderStatus.ts` follows for `cancelled`. **The last day of validity is a day of validity** (`<`, not `<=`), and **no validity date means the offer never lapses** — plenty are raised without one, and reading silence as expiry would condemn the lot. **It moves back**, for the same reason `completed` does on an order: extending the date is precisely how a lapsed quote is revived, and a status that stayed `expired` would make the extension do nothing. `status_before_expired` is filled **only when this code expires it**, so one marked expired by hand stays expired. The one subtlety worth keeping: reviving checks approval first. Editing a document resets its approval, and `sent` is an outgoing status, so a quotation whose validity was extended in the same edit comes back as a **draft** — without that check this would be an automatic path from unapproved to outgoing, the one thing `approval.ts` exists to prevent. The dashboard's `attention.expiringQuotations` changed with it, from *already lapsed* to **expiring within seven days**: once the status is set automatically, the old count would have been zero for ever and quietly stopped being a warning.
- **An invoice's `paid` status follows the payment record** (`services/invoiceStatus.ts`), the way an order's status follows the floor. `syncInvoiceStatus(id)` runs after anything that moves money — a payment created or deleted, an invoice created, edited, approved, status-set or deleted — so the pill the list shows is the pill stored. It differs from `orderStatus.ts` in the one way that matters: order status is **forward-only** because the floor's facts only accumulate, but a payment can be deleted and a total corrected upward, so this moves **back out** of `paid` too. An invoice still reading Paid after its payment was deleted is exactly the lie the feature exists to remove, and worse for looking automatic. Moving back needs somewhere to go, hence `status_before_paid` on the row: guessing `dispatched` would claim a shipment for an invoice settled by advance before anything left the plant, and guessing `final` would discard a despatch someone recorded. Setting `paid` **by hand** records the prior status the same way, so a rejected "mark as paid" puts the invoice back where it was rather than demoting it. Two invariants: the **approval gate is never bypassed** (only an already-approved, already-outgoing invoice is promoted, since `paid` is an outgoing status `approval.ts` guards), and **only currency-matched money counts**, because `invoiceReceivable` is asked rather than re-deriving the balance here.
- **Payments are scoped like documents**: `routes/payments.ts` resolves the linked PI/invoice and applies `canAccessCustomer` on create, and checks the payment's own `customer_id` on delete. Out-of-scope ids return 404.
- **An error the user can act on must not read as a fault.** The corollary of the delete-guard rule below, applied at the other end: `routes/masters.ts` validates a field's `oneOf` against the column's CHECK constraint rather than letting SQLite reject the insert as a 500 (`materials.category`, whose CHECK excludes `''`, also takes a `fallback` so an omitted category lands on the column default). Same reasoning as naming the despatch that blocks an invoice delete instead of leaving it to the foreign key.
- **Delete guards must cover every foreign key** pointing at the row, not just the obvious downstream document — a missed reference reaches the user as "Internal server error". Quotations are referenced by both `orders.quotation_id` and `proforma_invoices.quotation_id`; customers by quotations, orders, PIs, invoices, packing lists, follow-ups, payments and enquiries. The error handler in `index.ts` converts any remaining `FOREIGN KEY constraint failed` into a 409, but that is a backstop, not a substitute for a specific message.
- **Spreadsheet import** is two services. `services/spreadsheet.ts` is a dependency-free reader: an .xlsx is a ZIP of XML parts, so it walks the central directory, `inflateRawSync`s each part, and pulls cell text out of `sharedStrings.xml` + the sheet XML (shared/inline strings, sparse cells, multiple sheets; **dates come back as Excel serial numbers** — nothing interprets styles). It also parses CSV with delimiter sniffing. `splitHeader()` *scores* candidate rows on width and wordiness instead of taking the first plausible one, because real sheets have titles and merged two-tier banners above the real headings. `services/productImport.ts` maps columns to catalogue fields by heading synonyms and produces a per-row create/update/skip plan. **Preview and import run the identical pipeline** (`buildImport`) over the same re-uploaded file, so what the user confirms is exactly what gets written — keep it that way rather than trusting client-sent rows.
- **A product carries a type and a weight** (`services/productType.ts`, asked for by the user on 2026-09-04 for recipe and composition planning). Two columns, and the interesting part of each is what it is *not*. **The weight is grams per piece, which is the same number as kilograms per 1000 pieces** — the basis this catalogue is quoted, priced and recipe'd on, so one column serves the sales side and the factory side, and the form says the arithmetic out loud the way `RecipeModal` already does ("the commonest mistake here is entering grams per piece"). It replaces a convention rather than nothing: the line-item description placeholder has always read *"Item description incl. weight spec, e.g. (119 ±2) gms"*, so the figure the floor plans on was being typed into a sentence, per document, where it could not be summed or costed against. It is **nullable and never required** — the user's call, and the house one: the catalogue on file has ninety rows without a weight, so the list reports how many are blank (a `summary` over the whole filtered set, the shape `routes/despatches.ts` uses) rather than refusing anybody's save, exactly as `hasRecipe: false` and `unpriced_qty` report their gaps. `''` in a REAL column would be worse than useless — SQLite stores it as TEXT, it is not NULL, and it sorts above every number, so `weight_grams > 0` would be true of a product with no weight — which is why it joins `packingFields`, the list the import's `values()` consults to decide a blank's fallback. **The type has no CHECK constraint**, like `unit` and for the reason the proforma's `expired` status is derived: SQLite cannot ALTER one, and a vocabulary whose fourth entry is *Others* expects to grow; the enum is enforced in the route instead, answering 400 with the accepted list. It is **guessed once from the name** — word-boundary regexes in TypeScript, not `LIKE '%cap%'`, which would call *High Capacity Sleeve* a cap — and **a name matching two of the words stays `other`**, because choosing between *Preform Cap Combo*'s two readings would be inventing a fact. The pass runs only on the boot that creates the column (`addColumnIfMissing` now reports whether it added one), so a correction is never overwritten; measured on a scratch instance, 3 of 11 guessed, the second boot moved nothing, and a hand-set type survived it. Silence is guessed everywhere else too — `POST`/`PUT` read the name when no type is sent, so the form's explicit choice always wins and only an API call with nothing to say gets a guess. **The weight is deliberately never guessed**, though the names carry it: a wrong category is visible in a list and costs one click, a wrong weight is a number that flows into material planning looking authoritative.
- **Two traps in the import, one of them pre-existing.** `IMPORT_FIELDS` is matched in order and a claimed column joins a `taken` set, so the field declared earlier wins an ambiguous heading — and `name` carries the bare word `product` as a synonym. Measured against the code as it stood, the headers `Item Code | Product Type | Colour` mapped **name onto the Product Type column**, so such a sheet imported a catalogue of items called "Preform" and "Caps". `product_type` is therefore declared **first**, which takes that column back and changes no existing mapping (`product name` does not contain `type`) — verified header row by header row. And **an import no longer blanks a type or a weight the sheet does not carry**: the UPDATE sets every `importCols` column unconditionally, which is right for the columns a price list is *about* but would wipe the guessed types on the next import of one. The two new columns drop out of the SET when unmapped — the same reasoning as the photo, which "a spreadsheet never carries and an update must therefore leave alone". Measured: importing a price list with neither column updated two prices and left both types intact. `identityKey()` is **unchanged** and must stay so — adding weight to it would make the first re-import see every product on file (weight NULL) as new, and there is no unique index on `products` to stop the whole catalogue being written twice.
- **What a weight per piece does *not* do yet.** `PIECES_PER_BILLING_UNIT` in `services/totals.ts` still holds only `per 1000` and `unit`. Adding `kg` would put the derived branch ahead of `it.qty != null` in `billedQty`, so every kg-priced line carrying both a typed quantity and a piece count would stop billing on the typed one — and since the server recomputes on every save, the next PUT on an existing weight-billed document would restamp its amounts. That breaks the invariant `billedQty` states about itself: the fallback "only ever fires where the answer used to be null". Weight-based quantity is a later, deliberate change with its own proof, not a consequence of this column.
- **A product is identified by name + colour + pcs/box**, not name alone (`identityKey()`): the same item is genuinely stocked at two box counts, and those are separate things to quote and load. This key governs both in-file repeat detection and matching against the existing catalogue, so re-importing a sheet updates in place instead of duplicating. Imports never touch `image` — a spreadsheet has no photo to offer.
- **Numbering** (`services/numbering.ts`): pattern-based with `{FY}` (Indian fiscal year Apr–Mar, "26-27"), `{SEQ}` (3-digit) and `{SEQ4}` (4-digit) tokens, configurable per doc type in settings. Two widths because Aglo's books use both; padding is a minimum, so a series past 999 prints in full. `{SEQ4}` is substituted **before** `{SEQ}`, or the longer token would leave a stray `4`. Proformas and invoices have **separate export vs domestic patterns and sequences** (`isExport` option; sequence keys like `proforma_export`). **Every default matches Aglo's own paperwork**, read off the real documents rather than invented: proformas `AGLO/PI/{FY}/{SEQ}` and `AGLO/EX/{FY}/{SEQ}` (samples `AGLO/PI/25-26/094`, `AGLO/EX/25-26/118A` in `D:\Quotation Doc\`); invoices `AP/{SEQ4}/{FY}` and `AP/EX/{SEQ}/{FY}` (sample `AP/EX/101/25-26`, and `AP/0196/26-27` from the `Invoice No.` column of the desk workbook, where 35 entries split between `AP/####` shorthand and the full form). Note the **invoice puts the sequence before the fiscal year and the proforma after** — that is how they are written, not a slip. A migration in `connection.ts` moves rows still holding an old generic default and leaves any customised pattern alone; it never touches a `number` already issued. **The counter itself is settable** — `GET`/`PUT /api/settings/sequences`, manager-only in both directions (the GET guarded explicitly, since the mount lets any GET on `/api/settings` through and how many invoices the group has raised is not an employee's business). `sequences.next_num` stores the number last *issued*, so "next is N" is written as N−1. Moving a series **forward** is the point — an app taking over a book already at `AP/0262` must not re-issue what the customer holds — and moving one **backward** is refused unless `force`, because the collision would otherwise surface at save time to whoever happened to be raising a document. **The fiscal year comes from the document's own date** (`fiscalYearOf`), not from today: an invoice dated 31 March belongs to the year ending that day whoever raises it in April, and it draws from *that* year's counter, so back-dating neither mislabels the number nor eats one from the current series. The date string is parsed as digits rather than passed to `new Date()`, which reads a bare date as UTC midnight and then answers `getMonth()` locally — a 1 April document would fall into the previous year on any server behind UTC. Work orders have no date column and so are still numbered in today's year, which is right for an instruction issued now. A number is fixed once issued: changing a document's date afterwards does not renumber it, and the Number field is editable by hand if it must be. Numbers are consumed inside the create transaction, and every document's `number` can be manually overridden via PUT (forms expose an editable Number field on existing documents).
- **Totals** (`services/totals.ts`): `computeTotals(items, taxType, freight, insurance, currency)` — INR grand totals round to the whole rupee; PDFs derive the "Round off" line as `grand_total − (subtotal + freight + insurance + tax_total)`. Quotations carry freight/insurance too (the "Indicative Freight & Insurance" band).
- **Header freight and insurance are taxed** (confirmed with Aglo, 2026-08-18: they charge GST on both). They used to be added into `taxable` and then left out of `tax_total`, so every domestic document using the header fields under-charged GST by the tax on them; freight entered as a **charge line** was always right, because a line carries its own `tax_pct`. The header fields have no rate of their own and nowhere to put one, so — as a composite supply follows its principal supply under GST — the charge is **apportioned across the lines by amount and each share taxed at that line's rate**. With one rate on every line, the ordinary case, that is exactly `charges × rate`, and the two routes now agree: header freight lands on the same grand total as the same money entered as a charge line. A price-only document (no quantities, `subtotal` 0) has no rate to follow, so the charges attract nothing rather than a guessed rate. **Stored totals are not rewritten** — `computeTotals` runs on save, so a document already raised keeps its figure until it is next edited. Nothing on file was affected when this landed: the only document carrying header charges was an export proforma at `tax_type = 'none'`.
- **Which registration number goes on which document** (`registrationLine` in `services/pdf.ts`, confirmed with Aglo 2026-09-03). The three used to print on every document's letterhead together; the real rules are narrower. **GSTIN is domestic only** — an export sale is zero-rated and the buyer is abroad. **IEC is the export commercial invoice only** — it is the code the consignment clears customs under, so it belongs on the document travelling with the goods, not on a quotation or an order. **PAN is not printed at all**; the column stays, since dropping it would be a destructive schema change for a field nothing reads. The subtlety is that `exportDocGrid` — the boxed customs header on the invoice and packing list — **states the same numbers a second time**, so it takes the same `HeaderOpts` and calls the same helper; without that an export invoice dropped its GSTIN at the top and carried it in the exporter block below. The packing list follows its invoice's type and never carries the IEC, not being a commercial invoice.
- **The ARN/LUT reference belongs to the consignment, not the company.** A fresh one is obtained per export shipment, so `commercial_invoices.arn_ref` (additive) is entered on the invoice form, which offers the field only on an export. The company's `arn_ref` in Settings survives as the **default printed when the invoice's own is blank**, so nothing already raised changes what it prints. The packing list prints its invoice's reference, and both suppress it entirely on a domestic document — matching the form, which does not offer the field there.
- **PDFs** (`services/pdf.ts`): pdfmake with fonts decoded from its bundled vfs (no font files, no browser). Theme color comes from `settings.theme_color` (default maroon `#8b1a1a`). Shared helpers: `companyHeader` (logo left, company right), `docTitle` (letter-spaced underlined), `totalsBand` (theme-filled emphasis bars), `exportDocGrid` (the boxed customs header shared by invoice + packing list), `signatureBlock`, `notesAndTerms`. One builder per document type; served by `routes/pdf.ts` at `/api/pdf/<type>/:id`. The packing list pulls parties/ports from its linked invoice at render time.
- **The letterhead is as tall as its words, and no taller** (`companyHeader`, `LOGO_MAX_H`). Two things were opening a band of white between the address block and the theme rule, and both were invisible in the code. `registrationLine` returns `''` far more often than not — on every export document that is not a commercial invoice, and on any domestic one whose company has no GSTIN in Settings — and an **empty text node is still a line box**, so a blank line was printed with its margin and the rule pushed down after it. And the logo was fitted into an **80pt-tall box** while the text stack beside it runs about 52pt, so the row took its height from the image: a letterhead file with padding baked around the mark (the ordinary shape of one, and not something that can be cropped here — there is no image library and there is not going to be one) made the header a third taller for nothing. The registration line is now conditional and the logo box is capped. Measured by rendering the same quotation before and after at one scale, with a deliberately padded logo and no GSTIN: the rule moved from y≈195 to y≈161 and the items table with it, about **34pt** off the top of every page one. **The cap was then taken further** (2026-09-07, asked to make the mark smaller and sit higher), and measuring the cause is what made it a one-line change: the right-hand text stack is **48.95pt**, so at 56 the logo was the taller side of the `columns` row on any mark squarer than about 2.8:1 — the letterhead took its height from the image rather than from its words, which is the very thing the cap existed to stop. `LOGO_MAX_H = 44` puts it under the text for every shape, so the rule now lands at the same y whatever logo a company uploads, and `LOGO_LIFT = 4` is a negative top margin that sets the mark off from the block of type without touching the row height. The **width is deliberately untouched**: on the Aglo mark (~2.6:1) the height is what binds, so 158 never came into it. Measured on the same quotation at three aspect ratios — 3:1, 2.6:1 and 2:1 — the logo went 145×56 to 114×44 at 2.6:1 (21% smaller), its top edge 26 to 22, and the rule 86, 86 and 82.67 respectively to a flat **78.95** for all three.
- **A PDF is named for what it is, not for its number.** `routes/pdf.ts` used to serve every document as its number with the punctuation flattened — `AGLO_PI_26-27_001.pdf` — which is unambiguous inside the office and opaque everywhere else, starting with the customer's inbox. The name now reads *Proforma Invoice_Acme Maschinenbau GmbH_AGLO-EX-26-27-001.pdf*: what the document is, who it is for, and the number, which is the part that has to stay unique. Four things it has to get right. **A quotation revision carries its round** (`_R1`, numbered as the list labels it — the first round is revision 0 and prints nothing), because revisions share one number and without it the second one saved to a folder overwrites the first. **Windows' reserved characters become hyphens** and a trailing dot or space is stripped rather than substituted, since a name ending in either quietly loses its extension. **The name is served twice**: a lossy ASCII `filename=` and the real one in `filename*=UTF-8''` (RFC 5987), because a customer called *Émeraude* cannot be spelled in the first — measured, the fallback reads `_meraude` and the browser takes the second. And the **label is per type** (`DOC_LABEL`), so the combined invoice-and-packing-list file says it is both. And the name is in the **URL** as well as the header: these open *inline*, and a PDF viewer that builds its Save name from the address bar instead sees `/api/pdf/quotation/5`, whose last segment is a bare id — which is what "the file name is coming as a number" turned out to mean. A request with no name segment is **redirected** to one that has it (`/:type/:id/:name?`), so the address bar carries it too. The redirect rather than a name built by the client, because it is assembled here from the customer and the number and a second copy on the client is how the two come to disagree; it happens **after** the access checks, so it cannot confirm an id to somebody who may not see it, and **before** the render, so the extra hop costs a query rather than a document. Verified on a scratch instance across all six types plus the two 404 paths, with `?download=1` carried through the hop and an employee still getting 404 on the purchase order rather than a redirect naming its supplier.
- **The proforma's header grid picks its own shape.** Its four banner blocks (buyer, shipment, customs, bank) can sit as a 2×2 grid or as the buyer cell spanned down the left with the rest stacked beside it. Neither wins outright: a 2×2 row is as tall as its taller cell, so the grid pays only when the pairs are evenly matched, and the spanned form loses badly when the stacked right column outgrows the buyer block. `buildProformaPdf` estimates both heights from line counts and takes the shorter — worth ~16% of the space above the goods. Don't replace it with a fixed layout without measuring both against a document that has bank details *and* a full customs block.
- `settings` is a single-row table (id=1); `bank_accounts` is a JSON string column, parsed at the route boundary.

**Client** (`client/src/`, React 18 + Vite + Tailwind v4 + TanStack Query):

- Document pages come in pairs: a list page and a form page that doubles as the detail view (`/quotations/:id` etc.), with status pills, PDF link, follow-up button, and convert button in the header. `pages/QuotationForm.tsx` is the reference implementation.
- **The layout switches at `md` (768px).** Below it the sidebar is a drawer behind a hamburger in a fixed top bar, `<main>` drops its left margin and takes lighter padding; above it, everything is exactly as it was — verified at 375, 600, 768 and 1440. Three things to know. The drawer **closes on every navigation** (`useEffect` on `pathname`), because tapping a link and being left looking at the menu you tapped it in is the classic version of this bug; a backdrop closes it too, and is only rendered while it is open so it cannot swallow clicks the rest of the time. It is toggled with **`hidden` / `flex`, not a transform**: `-translate-x-full` → `translate-x-0` was tried first and silently did not move the panel — Tailwind v4 routes those through `--tw-translate-x` and the `translate` property, and with a `md:` variant of the same utility on the element the custom property resolved to `0px` while the computed `translate` stayed `-100%`. The cost is the slide animation, which is not worth the cascade archaeology. And the **field grids stack**: 35 unconditional `grid-cols-2/3/4` became `grid-cols-1 sm:grid-cols-N` (four short fields go to two-up rather than one-up). Anything that already named a breakpoint was a deliberate choice and was left alone, as was the dashboard's three-stat row, which reads fine at 101px a column.
- **`<main>` carries `min-w-0`** (`components/Layout.tsx`). It is a flex item, and a flex item defaults to `min-width: auto` — it will not shrink below its own content. So on any window narrower than the widest table, main stayed wide, pushed the document past the viewport and gave the whole app a horizontal scrollbar, on every page. Measured at 768px: the document was 815px wide with `auto` and exactly 753 with `0`. The tables still scroll inside their own `overflow-x` cards, which is where the scrolling belongs — the page body never should. Note this does **not** make the app usable on a phone: the sidebar is `fixed w-56` with no collapsed state, so at 375px it takes half the screen. That is a separate piece of work, not a bug.
- **`Input`, `Select` and `Textarea` default to `w-full` only when the caller has not set a width.** A default expressed as a class cannot be overridden by another class — `w-full` and `w-48` are both width utilities of equal specificity, so the winner is decided by stylesheet order, not attribute order. Passing a width did nothing reliable, and it stayed invisible for months because a non-wrapping flex row squashes its children anyway; put the same controls in a **wrapping** row and every one claims full width and drops onto its own line, which is how the dashboard header broke. `setsWidth()` in `components/ui.tsx` reads the class string and suppresses the default — deliberately not a class-merging dependency, and deliberately blind to `max-w-*`, since `w-full max-w-sm` is a legitimate pairing.
- **The proforma form is one screen, not two.** It asked for the same fifteen fields in a shape that never changed: three columns on every window, so a 1900px desktop got three fields half the width of the screen each holding "USD" and a date, and four cards of chrome for what is one question in three parts. Four changes, measured on a new export proforma at 1900×1000 — **1441px down to 1010px**, which is the Create button now above the fold rather than a page below it. The **grid steps** (`FIELD_GRID` in `components/ui.tsx`, and `FIELD_GRID_PLAIN` for read-only): one column, two on a tablet, three at `lg`, four at `xl`, with the row gap tightened since a box already separates a field from the one under it — read-only keeps its wider gutters, having no boxes to do that job. The **buyer's PO folds into Details**, where it belongs: it was a card with a header and 32px of padding around a single row of two fields. **Consignee & Notify Parties and Export Details become `Shipment & Parties`** — where the goods go and who is told about it was three cards asking one question between them — and the party boxes drop to two rows, holding an address and scrolling for the rare longer one. And **Container Fitment renders nothing until a goods line exists** (`ContainerFitment.tsx`, the return placed **below** the hooks): on a new proforma it was a whole card, above the fold, reporting an absence, and the question it answers does not arise until there is something to load. **All five document forms use that grid**, which is why it is one exported string rather than four copies — four copies of a layout is how three of them end up slightly different from the fourth. **The quotation took the grid and nothing else**, `gridClass` being the one piece of that work that transfers: it has no cards to merge and no fitment panel, so the change is the stepping and the tighter rows, plus dropping the two `<div />` spacers — they pushed the next field onto a fresh row, which only means anything while the row is three wide, and with a grid that steps they would land somewhere different at every size. Measured the same way, 1900×1000: its Details card goes **408px to 329px** and the page 738 to 659. It was already inside one screen, so this is breathing room rather than a rescue. **The order took the grid on its intake fields only** — its Production Plan is four short dates already four-up and its Remarks is two textareas side by side, and both are deliberate shapes rather than the one-size-fits-all three; 1052px to 987. **The commercial invoice took the grid and the proforma's merge**, having the same two cards asking one question: Consignee & Notify Parties and Export Details are `Shipment & Parties` there too, with the party boxes two rows deep. Domestic, 1405px to 1239. A *saved* one carries its number as well, and four fields is two rows at three columns and one row at four: 252px to 191, the page 859 to 798. Worth stating rather than quoting the flattering number alone.
- **The client can be looked at, in a harness.** The preview browser has no session, so the app cannot be driven — but a page can still be *rendered*: a throwaway `client/harness.html` + `src/harness.tsx` mounting the real component under `createMemoryRouter` (a **data** router, or `useUnsavedChanges`'s `useBlocker` throws) and a `QueryClientProvider`, with `window.fetch` stubbed for `/api/*`. - **The surfaces are all in `components/ui.tsx`**, which is what makes a visual change a one-file change: fields carry a soft `slate-200` border, a hover border so a control answers the pointer, and a 2px `brand-600/25` focus ring in place of the old hard 1px one, which read as an error state; cards are `rounded-xl` with a tinted header strip; status pills are a tinted face inside a ring rather than a solid block of colour; buttons and every other control in the file share the radius. **Padding is untouched, deliberately** — this landed straight after several rounds of compacting the forms, so it changes borders, colour, radius, shadow and type and nothing that takes layout space. - **The dashboard took the same pass, and it is where a page file finally had to be edited.** The visual work stopped at `components/ui.tsx` on purpose, but this page had grown its own copies of what that file owns: the money tiles and the attention strip were built as bare divs at the *old* card look — `rounded-lg`, a hard `shadow-sm`, no header tint — sitting in a grid of twelve real Cards wearing the new one, which is the one arrangement where a restyle looks like a bug. The prefill endpoints do not carry `validity_date`, so the default survives a carry-forward rather than being spread over. **The consequence worth knowing** is that this makes the expiry sweeps bite: `quotationExpiry.ts` lapses a `sent` or `negotiating` quotation past its validity, and `STATUS_SQL` derives `expired` for a `draft` or `sent` proforma, so documents that used to carry no validity date and therefore **never lapsed** will now go `expired` after a week unless the date is extended. That is what was asked for; it is stated here because it is the sort of automatic status change that reads as a fault when nobody expects it.

- **Leaving a form with unsaved edits asks first** (`lib/useUnsavedChanges.ts`), on all five document forms. The hook therefore renders, which is why the file is `.tsx` and why it returns a `prompt` node each form drops at the end of its tree. Three things it has to get right. **The destination is read before the save, not after**: saving a *new* document clears the dirty flag and then navigates to its own id from the mutation's success handler — which passes the blocker, being no longer dirty — so by the time `await` returns, the block being held is gone and `proceed` with it; measured, Save landed on the new quotation instead of on the page asked for, and it now navigates to the remembered location, which covers both cases. **A refused save keeps the dialog open** with the server's own sentence on it and the navigation still blocked, since proceeding would lose the edits the button exists to keep. And **Save is offered but disabled when the document cannot be saved at all** — `can` is the same condition the page's own Save button carries (a customer and at least one line), and the dialog says why rather than offering a button that only produces a 400. Verified in a harness driving the real route table: an untouched form leaves silently, an edited one holds the navigation, Cancel stays put, *Don't save* leaves with nothing written, Save writes once and lands on the destination, a 409 keeps the dialog open showing the server's message, and a document with no lines gets the disabled button and the reason. **There was a fourth way out that neither half could see**, and it was the one that reached the customer: a PDF link is an `<a target="_blank">`, so `useBlocker` never hears the click and `beforeunload` never fires — the current tab is not being left. Editing a quotation and clicking 📄 printed the **last saved** version in silence, and that is the file somebody attaches to an email. It would have stayed unreported too, the PDF that opens being a perfectly normal document, just not the one on screen. `components/PdfLink.tsx` asks `isDirty()` on the click. Two decisions in it. **The sentence is not the navigation one**: leaving the page loses the edits, opening a PDF loses nothing at all — the form is still there in the tab behind it — so the hazard is a *stale document*, and a prompt saying "lose them?" about an action that loses nothing is how people learn these dialogs are wrong. It states the fact and still opens on request, which is often what was wanted: checking what was already sent against what is now being typed is a real thing to do. And **`isDirty` is a required prop rather than a context**, which is the opposite of the call `ReadOnlyFields` makes about the same spread-out problem — because a context is forgotten by *not wrapping*, and a missing provider is silent: the links render, nothing prompts, and the failure looks exactly like success, which is the shape of the bug being fixed. A required prop is refused by the compiler instead. Links **outside** a form stay plain anchors (the approvals queue, the QC register, the purchase-order rows): those point at documents as the server holds them, so no draft can be ahead of the file. Verified in a harness driving the real hook across five cases — an untouched form opens silently, an edited one prompts and Cancel blocks the open while OK allows it, a save returns it to silence, and an edit typed and then undone by hand prompts not at all. Verified against a throwaway two-route harness driving the real hook: a draft that changes itself after mount does not prompt, typing outside the draft does not prompt, an edit undone by hand does not prompt, an edit does, Back is blocked and the URL restored, and `beforeunload` is silent before the edit and after the save.

- **Container Planner** (`pages/ContainerPlanner.tsx` + `lib/containerPlan.ts`) answers the loading question. Capacity is not a single number — different products box up differently, so one box of product *i* occupies `1/Cᵢ` of a container (`Cᵢ` = its `qty_20ft`/`qty_40ft`) and any mix must satisfy `Σ(boxesᵢ/Cᵢ) ≤ containers`. Two modes solve that in opposite directions: *fill* scales a requested ratio until the containers are exactly full, floors to whole boxes, then hands the rounding remainder back largest-deficit-first; *requirement* rounds pieces up to whole boxes and reports containers needed plus leftover room. The ratio basis (boxes vs pieces) changes the answer dramatically — an equal *piece* split of caps and handles is ~94% handles by volume — so keep both bases available. **One plan covers one container size**, since space is expressed as a fraction of its own container type. ## Deployment

Production is **one service on one origin**: Express serves `/api` and, when `client/dist` exists, the built React app plus an SPA fallback. The root `package.json` is the deploy entry point (`build` → client build + production install; `start` → the server); `render.yaml` is a working blueprint for Render with a disk at `/data`.

- **`tsx` is a runtime dependency, not a dev one** — the server runs TypeScript directly in production. Compiling would need an emitting tsconfig *and* an asset copy for `schema.sql`, which `db/connection.ts` loads relative to `__dirname`. Don't "fix" this by moving tsx back.
- **Env vars that matter**: `DATA_DIR` (the disk mount), `NODE_ENV=production` (switches on `trust proxy`, `secure` cookies, and switches *off* CORS since it's same-origin), and `JWT_SECRET` (≥32 chars, enforced at boot — without it every redeploy signs everyone out).
- **Never scale past one instance.** SQLite is a file on that disk.
- **Locked out? `npm run reset-password`** (`src/db/resetPassword.ts`), run in `server/` where the database is — the Render shell, or a terminal beside `server/data`. There is no forgot-password flow in the app and deliberately shouldn't be: there is no mail server, and a reset link nobody can receive is worse than none. This puts the recovery where the disk is, which is the same authority the disk already grants — anyone who can run it could read the database anyway. With no arguments it lists the accounts; with `--email` it resets one. It **generates the password rather than accepting one**, because a password passed as an argument lands in shell history and, briefly, in the process list; there is no `--password` flag and adding one would be a step backwards. It **bumps `token_version`** like `PUT /users/:id` does, so every session on that account dies — verified against a running server, whose live session went 401 without the process ever learning about the reset — and it **writes to `audit_log`** with no actor and a note saying it came from the command line, since this is the one path that bypasses HTTP entirely and a password changing with nothing in the trail is the hole the trail exists to close. A deactivated account is reported and **left deactivated**: switching one back on is a decision, not part of a password reset, and `--activate` is how you say so.
- **Backups** (`services/backup.ts`): `VACUUM INTO` on boot and daily into `$DATA_DIR/backups/`, 14-day retention, plus manager-only `GET /api/backup/download`. That route is mounted at `/api/backup`, **not** under `/api/settings`, whose guard lets any GET through — putting it there would make the whole database downloadable by every employee.

- **Quality control** (`services/qc.ts`, `product_qc_params` + `qc_checks` + `qc_results`): the recipe's twin — a short spec per product, rewritten whole, edited in its own dialog. A parameter is a **measurement** with a tolerance (either end may be open: a wall can be too thin and never too thick) or a **pass/fail** for the eye, which is what a multicolour range needs. **Pass and fail are never stored**: a result holds the reading and the tolerance, and `resultOk()` does the arithmetic — the same rule as balances in `stock.ts` and value in `costing.ts`. **The tolerance is copied onto the result** when the check is saved, so tightening a spec cannot retroactively fail a batch that met the spec of the day; the parameter's `name`, `kind` and `unit` are copied too, and `qc_results.param_id` is `ON DELETE SET NULL`, so rewriting the spec whole leaves the history readable rather than 409ing on a foreign key (it did, first time). **A parameter left blank was not measured** — it is not stored, is not a failure, and a check with nothing in it is refused rather than saved as a pass. **A product with no parameters has no opinion**: `has_spec: false`, never "everything passed", exactly as `hasRecipe: false` is not a requirement of zero. Checks hang off the work order and are scoped through its order like every other floor action.
- **A customer may have their own tolerances** (`product_qc_params.customer_id`, nullable and additive, asked for 2026-09-05). NULL is the product's default; rows carrying a customer are **that customer's, and they replace the default rather than merging with it** — the same part is genuinely measured to different dimensions for different buyers, and a spec assembled out of two lists is one nobody can check by reading it. So there is one list, and `specOwner()` says whose: `customer`, `default`, or `none`, which is still no opinion rather than a pass. `paramsFor(productId, customerId?)` grew the second argument and every reader passes it — a check hangs off a work order, which carries `order_id`, which carries `customer_id`. **Nothing about history changed**, and that is the point: `qc_results` already copies the tolerance onto the result as the check is saved, so the rule that protects a batch from a spec tightened later now also protects it from *another customer's* spec. Measured on a scratch instance: a reading of **0.45 mm passes the product default of 0.3–0.5 and fails the customer's own 0.38–0.42** — the whole feature in one figure. Writing a customer's list never disturbs the default, and clearing it puts them back on the default, which is the only way to withdraw an override; the dialog therefore opens on whatever is *in force*, so saving an inherited list is how an override is created.
- **The quality report is four documents over one builder** (`qcReportContent` in `services/pdf.ts`): `qc-report/:workOrderId` for one job, `order-qc-report/:orderId` for every job on an order, `invoice-qc-report/:invoiceId` for the jobs behind a shipment, and `invoice-with-qc/:invoiceId` — the invoice, a page break, then the summary, which is `buildInvoiceWithPackingPdf` verbatim in shape **including how it degrades**: an invoice whose jobs carry no checks comes back as the invoice alone, never as an invoice followed by a page saying nothing. The body is **grouped by date and shift**, which is what "shift wise details" asked for and the first thing in this app to group on `shift`, a column that has always been free text. Each reading prints beside **the tolerance it was judged against** — the copy on the result, not today's spec — and the report says whose specification applied. **Finding the jobs behind an invoice** reuses `dispatchProgress()`'s walk (`commercial_invoices.order_id`, or `pi_id` → a proforma carrying one) and then the chain's **index rule**: an invoice line at position *i* bills the order line at position *i*, and `work_orders.order_line` is that position — positions count charge lines, so nothing is compacted first. `routes/pdf.ts` gained an optional **`partySql`** for the three that hang off a work order or an order rather than a document with its own `customer_id`; the map already special-cased the supplier side, and one field naming the query generalises both instead of adding a third. Each entry names its `fn`, so `qc-report` is 404 for Sales and served to Quality and Production, while **`invoice-with-qc` is gated as an invoice** — Quality and Production are refused it, deliberately, since the file *is* a commercial invoice.
- **The QC register is `GET /api/work-orders/qc-checks`** — every inspection, newest first, filterable by date range, customer, product, process and verdict, and paged. It lives in the work orders router because it is the `qc` function on a record that hangs off a work order: the mount, the scope clause and the customer join were already there. It must stay declared **above `/:id`**, or Express reads "qc-checks" as a job id. The interesting part is that the **verdict is computed in SQL** — `RESULT_FAILED_SQL`, which is `resultOk` restated. Two copies of a rule is what this codebase normally refuses, and the precedent is `orderLines.ts` reproducing `dispatchProgress()`'s index rule in one statement: the list is paged, so a verdict derived after the fetch could only filter and count the page in hand. What makes it safe is that the two are not assumed to agree — `qcRegister.test.ts` runs both over **100 combinations** of kind, reading and open-ended bound and asserts they answer identically, including the mapping that matters: *nothing measured* is not a failure, and is not a pass either, which is why `measured` is counted separately. The summary is over the **whole filtered set**, never the page. Client side `pages/Quality.tsx` holds every filter in the URL through `useUrlFilter`.
- **A job names a process** (`processes`, the seventh master; `work_orders.process_id`, a fourth nullable master FK of exactly the shape `location_id`/`machine_id`/`mould_id` already had). Seeded with **Assembly** and **Camera inspection** on first boot, the way a location and a "Self" transporter are — a master with nothing in it is a field nobody can fill. Moulding is not the only thing a job can be, and the quality report prints which was done.
- **`semi_finished` is the fifth product type.** The original note said this axis was the shape of the goods and *not* a procurement class; the user then asked for exactly that value, and they are right about their own catalogue — a semi-finished item here is a distinct thing they stock and sell on, not a stage. Raw materials stay their own master, so the other axis is still separate where it matters. It cost one line on each side, which is what the missing CHECK constraint was for, and **re-typed nothing on file**: the guess runs only on the boot that creates the column, and by the ambiguity rule a name matching two words was `other` anyway.
- **Recipes** (`services/recipe.ts`, `product_materials`): what a product consumes **per 1000 pieces**, the basis the whole catalogue is quoted on — a 119 g preform is 119 kg of resin per 1000. **A product with no recipe reports `hasRecipe: false`, never a requirement of zero.** Zero reads as "needs nothing" and would make a shortfall report claim every job is covered; every caller must surface "not costed" instead. The real sheet records material as one word (`HDPE`), so having no recipe is the normal starting state.
- **Work orders** (`routes/workOrders.ts`, `services/production.ts`): one job = make this many pieces of one order line, keyed by `order_line` position like the rest of the chain. **Progress is never stored** — produced/rejected/balance/reject-rate are sums over `production_entries`, so deleting a mis-keyed shift corrects the figure by construction. An over-run does not make the balance negative. A line with no job reports `work_orders: 0` so the screen can say *not started* rather than *nothing made*. Scoped through the order's customer; **no approval workflow** — a work order is an instruction to ourselves, the same reason orders carry none.
- **Jobs are raised for a whole order in one press** (`POST /api/work-orders/bulk`, `BulkRaiseModal` in `components/ProductionTab.tsx`, asked for 2026-09-10). A four-line order needed four presses of **+ Job**, each opening a dialog only to accept the figure the app had already worked out — the figure being the same one every time, the typing was the entire cost. **Deliberately not an automatic conversion on order approval**, which is the shape an MRP would take, and the reason is this app's own access matrix rather than taste: raising a job is `work_order: full` — Production and the super admin — while **Sales, which confirms the order, holds `view`**. Auto-raising on approval would have Sales issue shop-floor instructions without holding the permission to. The second reason is that the quantity to plan is not always the quantity ordered; a partial run is ordinary here. So it stays a Production act with every figure on screen and editable, and it saves the presses rather than the judgement — machine, mould, process and dates are still set on each job afterwards.
- **It is one request, therefore one transaction.** Six jobs are one act: six separate posts would draw six numbers and leave an order half planned when the fourth failed. Measured — a press naming one good line and the freight line writes **nothing at all** and answers with the freight line's name. `insertJob` was factored out of the single raise so a job is created in exactly one place, the reason `saveItems` is one function per document, and `syncOrderStatus` is called **once for the press** rather than once per job.
- **The client chooses the lines and the server refuses nonsense**, rather than the server deciding what "still needs a job" means. That figure is a prefill shown in a form somebody can disagree with, so computing it on both sides would be a second copy of it; what the route checks is what only it can know — that the caller may see this order, that each line is really on it, that a **charge line is never made**, and that a quantity is above zero. Positions count charge lines, the chain's index rule: the fixture deliberately puts freight at position 1 so lines 2 and 3 have to land on products 2 and 3, and they do.
- **Writing it found the single raise over-planning, and fixed both with one rule.** `+ Job` prefilled *ordered − made*, which is right only on a line with no job: a line ordered at 1,20,000 with a job for 40,000 and 30,000 made prefilled **70,000**, when 40,000 of that is already somebody's instruction — so accepting the default double-planned 30,000 pieces. `stillToPlan()` is *ordered − **planned***, used by the bulk raise and by `+ Job`, because two copies of one question on one screen is how the two come to disagree. The two answers coincide exactly where the old one was ever right (a line with nothing planned has nothing planned), so no ordinary case changes. Both figures stay visible and distinct on the tab: the **Left** column is still ordered − made, which is what is left to *make*; the dialog offers what is left to *plan*.
- **A line that already has a job is offered but starts unticked**, since raising a second against it is a real thing to do and a decision rather than the default; one with nothing planned starts ticked, which is the ordinary case and the whole point of the button. A list rather than a confirm, because the two things somebody wants to change before pressing are *which* lines and *how many* pieces, and a yes-or-no about a figure nobody can see is how these get pressed blindly. The button disables itself, with the reason on hover, when every line is already covered.
- **And it closed a small hole beside it**: `+ Job` was rendered for everybody, so **Sales — `work_order: view` — was offered a button that only ever answered 403**. Both buttons now sit behind `can('work_order', 'full')`, and the empty state stops pointing at a control that is not there.
- Verified over HTTP on a scratch instance: a charge line refused by name, a line not on the order refused, a zero quantity refused naming the line, an empty list refused, one bad line refusing the whole press with nothing written, then **three jobs in one press** — `WO/26-27/001..003`, each carrying its own line's `product_id` (which is what the QC gate reads), the order moving `confirmed → scheduled` once. Across all five logins: Production and the super admin **201**, Sales, Logistics and Quality **403**. Rendered in a harness on the real route table at 1440x900 and looked at: the dialog lists the three goods lines and **not** the freight line, the part-planned line comes up unticked offering 60,000 where the row behind it reads 70,000 Left, and the button reads *Raise 2 jobs*. **No unit tests**, deliberately and consistently with this codebase: the rules here are route-level validation and a client prefill, and neither has a test layer — the same call `boxesFor` and `editTrip` record, both verified in a harness. The harness was deleted; 416 pass.
- **Material** (`services/stock.ts`, `material_moves`): **one signed ledger**, positive in, negative out, per material **and location**. There is no stock column anywhere, so a balance cannot drift from its history. `onHand`/`onOrder`/`shortfall` live here and nowhere else, the way `receivables.ts` owns credit. **Shortfall counts what is still to make** (planned − produced) — material for pieces already moulded has been consumed, and counting the whole plan again would order resin twice. Issuing more than is on hand is allowed and shows negative: the material physically left, and hiding it would make the ledger agree with the paperwork instead of the store.
- **What material is worth** (`services/costing.ts`): **moving average**, chosen with Aglo (2026-08-21) over FIFO — the resin is bought in bulk at similar rates, so layer tracking buys little, and an average is forgiving of a ledger corrected after the fact. **Nothing is stored**: there is no average column and no stock-value column, for the same reason there is no stock column. The figures come from **replaying `material_moves` in `date, id` order**, so deleting a mis-keyed receipt corrects the valuation exactly as it already corrects the quantity. What *is* stored is `material_moves.rate` on the way **in** — what a unit cost on arrival, stamped at receipt rather than read back through `po_id`, because editing a purchase order months later must not rewrite what the stock in the shed cost (there is a test for precisely that). **Valuation is per material, group-wide**, not per location like quantity: a kilo is worth the same at either plant, and a per-plant average would make a lorry between Jungalpur and PACK SKRL change the company's stock value. An **in** movement with no rate adds quantity but **stays out of the average's base** — entering it at zero was tried and makes unpriced stock look free, dragging every later average down (500 kg unrated plus 500 kg at 80 came out at 40, a claim that half the shed cost nothing). `unpriced_qty` reports how much is being valued by extrapolation, the way `hasRecipe: false` reports an uncosted product; the fix is to record a rate on the opening balance, not to read silence as zero. An **out** movement takes the average without changing it and draws the priced pool down first. `materialCostByWorkOrder()` gives cost per job, `orderMaterialCost()` per order — **partial by nature**, so `jobs_without_issues` rides along and the screen says so rather than letting a margin be read off half a job.
- **Purchase orders** (`routes/purchaseOrders.ts`): manager-only in full, mounted with `requireManager`. Same shape as the money documents (`saveItems` + `computeTotals`, with `rate` standing in for `unit_price`). **Received is never stored** — it is a sum of the `po_receipt` moves carrying that PO, which is what lets a part delivery be booked once and still move the status to `part_received`/`received` correctly.
- **The purchase order is the fourth document, and it took the shape of the other three** (2026-09-04, against Aglo's own reference order `Alternicq-PO-Preform 2925 12GRM .pdf` in `D:\Quotation Doc\`, which is its spec exactly as the Sanya and Emeraude samples are the quotation's and the proforma's). Four things came with it, and the first is the one to know. **A delivery is booked against a line, not a material.** How much had arrived used to be a sum over `material_moves` grouped by `material_id`; the comment said "per line" and it was not — two lines of one material each reported the other's delivery, and a line naming no material reported nothing for ever, so an order carrying one could never close. `po_receipts` records it per line, keyed by **position** because `saveItems` deletes and reinserts every line on each save, the same index rule `work_orders.order_line` and `dispatchProgress()` use. **Two records, one transaction, two questions**: `po_receipts` is what arrived against this order, `material_moves` is what that did to the stock — written only for a material line, since there is no finished-goods ledger and `material_moves.material_id` is `NOT NULL`, which SQLite cannot relax without rebuilding the table. Measured: 400 kg booked against line 0 of a three-line order leaves line 2, same material, reading nothing; receiving the rest closes the order *including its product line*; stock takes only the material lines and the moving average comes out at each line's own stamped rate. The backfill for deliveries already booked spreads them **earliest line first, capped at what each ordered** — `receivables.ts`'s rule for allocating an advance. Putting the lot on the first matching line was tried and measured worse: 1600 against a line that ordered 1000, nothing against the line that took the other 600.
- **A purchase order line names a material *or* a product**, at most one, neither being a free-text line, which was always legal. Aglo buys finished and semi-finished goods in — the reference order is for preforms — so the picker is one `SearchSelect` over both masters with the kind and the unit in the hint and the keywords, and **the unit comes from whichever master was picked** rather than the hard-coded `'kg'` on both sides. `po_items` gained the three packing columns every other item table has, which is strictly additive to the money: `billedQty` derives a quantity from `total_pcs` only on the piece bases, and every line on file is `kg` with a typed `qty`. Two guards that did not exist: `routes/products.ts` had **no delete guard against `po_items`**, so deleting a product would have orphaned a line, and `saveItems` reads what was bought back out of the *original* row by index after `computeTotals`, so `product_id` has to ride along the same way `material_id` does.
- **TCS is the one figure charged on the whole document rather than on a line**, so it lives on the header and `computeTotals` takes a `tcsPct` defaulting to 0 — charged on the taxable value *and* the tax on it, which is what the reference order adds up to. At 0 every figure is what it was before TCS existed, and there is a test across the tax-type × currency × freight matrix asserting exactly that, because the server recomputes on every save and a moved default would restate documents already raised. The PDF derives its **own** round-off rather than calling `roundOffOf`, which knows about freight and insurance and not about this: through that helper, ₹165.20 of tax would have printed as a rounding difference.
- **The purchase order PDF is the one addressed to a supplier, and the one that is manager-only.** Both facts are load-bearing in `routes/pdf.ts`: `purchase_orders` has no `customer_id`, so the shared customer join throws on it, and `/api/pdf` is mounted `requireAuth` while the module itself is `requireManager` — registering a builder without a per-entry guard would have published every supplier rate to every employee through a route nobody thinks of as part of that module. Verified: 200 and a 36KB file as a manager, **404 as an employee**. `registrationLine`'s rules deliberately do **not** transfer — they were written for an export *sale* (GSTIN domestic-only, IEC on the export commercial invoice) — so a purchase prints the company's GSTIN on both variants and never the IEC. **Imports get their own series**, `po_import_pattern`, added to `numbering.ts`'s `patternColumn` — one line that also creates the second sequence key, the second Settings row and the `exportChangeError` guard. The column is `is_import`, not `is_export`, because on a purchase the foreign party is the seller; the flag column and the *word* are carried in `patternColumn` so the refusal says "from the import series" rather than inheriting a sentence about exports. Measured: `PO-IMP/26-27/001` while the domestic book carried on at `PO/26-27/002`, and a flip afterwards answered 409.
- **The shortfall can be asked of the order book, not just of the jobs raised from it** (`ShortfallBasis` in `services/stock.ts`). The jobs basis counts `planned − produced`; the order basis counts `ordered − produced` over the goods lines of open orders, which is the same figure one step earlier — before anybody has raised a work order. They are **alternatives, never added**, since a planned-but-unmade piece is also an ordered-but-unmade one. Quantities come from `services/orderLines.ts` rather than a second walk of the same tables, which is also what drops charge lines at the source; a product with no recipe goes to `uncosted` and is named, never counted as zero. The **default stays `jobs`**: the dashboard's "materials short" chip has counted open work orders since it was written, and changing what a figure counts without changing its words is how a number quietly stops meaning what its reader thinks — the buying screen asks for `orders` explicitly and says on screen which it answered. Measured on a scratch instance: an order for 50,000 pieces of a product needing 119 kg per 1000 reported 5,950 kg required, 1,600 on hand, 10 on order, **4,340 short** — while the jobs basis reported nothing at all, because no job had been raised. That gap is the whole feature.
- **A purchase order can be raised from the shortfall.** `GET /api/purchase-orders/prefill/from-shortfall` is the carry-forward pattern with the shortfall standing in for a source document — hence **no id in the path**, since "what are we short of" is one question about the whole factory. It must stay **declared above `/:id`** or Express reads "prefill" as an id. `services/purchasing.ts` owns it: it asks `stock.ts` for the shortfall rather than re-deriving it, and adds the two things a buyer needs before a figure becomes an order — **who we last bought each material from, and at what rate**. Neither is stored; `materials` deliberately has no supplier column, because a material is not one supplier's property and writing one on would make a second quote for the same resin look like a different material. Both are derived by `ROW_NUMBER` over the purchase history in one statement, which also makes the suggestion self-correcting. **Cancelled orders are excluded** — a rate nobody bought at is not what we last paid — while drafts are kept, with the date and number returned so a stale suggestion is visible. A rate only carries across when the last purchase was **in the same currency** as the draft, the same rule `receivables.ts` applies to a payment. `?supplier_id=` narrows to that supplier's materials (one order goes to one supplier) and sets `filtered` so the screen can say something was left out. **`uncosted` rides along and must be surfaced**: a job whose product has no recipe needs an unknown amount, not none, so an order raised from this may still be short — the client shows it as a warning above the groups.

- **A despatch line has a ceiling and a floor** (`services/despatchLimits.ts`, asked for 2026-09-07). - **Both rungs are derived now, or the hole is only slid one along.** `anyJob` implies `confirmed`; a job that is **actually going to run** implies `scheduled`, and either explicit act counts — **released** to the floor, or given a **start date**. Which of the two a desk uses varies: the date fields are often left blank here, and releasing three jobs at once is a normal order-level act. A job merely raised is neither — it sits at `planned` with no date, and that is exactly what *Work Order* now means. Cancelled jobs count for nothing, as they already did everywhere else.
- **Verifying it found the two job routes that never re-synced the order**, and one half of that was wrong before any of this. `PUT /work-orders/:id` and `POST /work-orders/:id/status` both changed inputs the ladder reads and neither called `syncOrderStatus` — so with the new derivation nothing would ever have reached `scheduled`, and with the **old** one **cancelling the last job on an order left it claiming *Scheduled* over an empty floor**. That is the same defect the ladder rework of 2026-09-10 went looking for: it found the three *delete* routes that never synced and missed the status route, which cancels. Both call it now. This is deliberately the opposite call to the **despatch PUT, which still calls nothing** — that one edits a trip's lines, dates and references while `impliedStatus` reads only the despatch *count*, so a call there would be symmetry rather than correctness. Here `planned_start` and `status` are inputs, so it is correctness.
- **Existing orders correct themselves lazily rather than by a migration.** Nothing rewrites the book on boot; each order settles the next time a job, shift, despatch or invoice touches it, and the ladder moves both ways so it settles correctly whenever that is. An order sitting at an automatic `scheduled` with only a raised job will therefore read *Scheduled* until something happens to it and then drop to *Work Order* — which is the right value, arriving late. A one-off pass calling `syncOrderStatus` over every order would settle the lot at once and is a five-line addition to `connection.ts` if the mixed reading turns out to be worth removing; it was left out because the book is small, the drift is cosmetic, and rewriting every live order's status on a boot is a larger event than the thing it fixes.
- Measured over HTTP on a scratch instance, walking it in both directions: a bare order **pending**; a job raised through the bulk action (status `planned`, no dates) **confirmed**; a start date **scheduled**; the date removed again **confirmed**; released **scheduled**; output booked **in_production**. Then the hole that was there before: with one job and production against it, cancelling that job takes the order **in_production → pending**, and un-cancelling puts it back. `orderStatus.test.ts` grew from 12 cases to 17 — the five new ones cover the two rungs, both directions and a cancelled job — and the existing *"raising a job should schedule the order"* assertion was corrected to say *released*, its fixture having created released jobs all along, which is why every one of them kept passing through a change that altered what a bare job implies.
- **`status_before_auto` is that floor, and it replaces `status_before_completed`.** The old column was a memory for one rung — where to re-open an automatically closed order to — built when `completed` was thought to be the only status that could move back. The same hole ran the length of the ladder, so the memory does too: it holds the status in place **before this code first raised the order above it**, and is empty whenever the status on the row is a person's own. That is what makes "is this status ours or theirs?" answerable from the row itself rather than from a flag that could disagree with it, and it is cleared the moment the order comes back down to the floor. Setting the status by hand clears it — which is what keeps an order **closed by hand** closed however the invoices later add up, the commercial decision (a short shipment accepted) the original design was right to protect. It also does what a per-rung memory could not: an order set to `ready` by hand, raised to `partially_dispatched` by a lorry, returns to **`ready`** when that despatch is deleted rather than falling to what the facts alone say. `completed` still measures on the **invoice walk** (`fullyBilled()`), not the despatch record — `dispatchProgress()` has always been the money truth, and closing on the paperwork is the conservative direction; charge lines are excluded and a line with no quantity can never be complete. The old column is **kept but unwritten**, dropping one not being an additive change, and the boot **seeds the new one from it**: on a row that carries a value it means exactly the same thing. Every other order starts with **no memory**, so an order already on file is treated as standing where a person put it and is never silently lowered — the conservative direction every `status_before_*` in this codebase takes, and it means only orders raised from here on come down the ladder. Verified on a scratch instance planted with pre-migration rows: the row holding `ready` was seeded with it, the row holding nothing was left alone, and a second boot moved neither (a hand-set memory survived it). Then over HTTP: an order walked `pending → scheduled → in_production → partially_dispatched` as a job, a shift and a lorry were recorded, and **all the way back down** as each was deleted; one set to `ready` by hand went to `partially_dispatched` and back to `ready`; and one closed by hand stayed closed. `orderStatus.test.ts` is new — twelve cases over a service that had none.
- **The dashboard says what the sea leg is doing** (2026-09-08). Two chips in the attention strip — *shipments awaiting documents* (red) and *shipments arriving this week* (amber) — beside the despatch count that was already there. They answer the two questions an export desk asks every morning and the dashboard could not, though the register has held the columns since they were added. **Papers outstanding is red** because the buyer cannot clear the goods without them: a container at the port with its documents on somebody's desk is the most expensive row in the book. **An arrival is not a fault**, so it is amber, and the window is seven days to match `expiringQuotations` beside it — near enough to act on, far enough to be ready for. An **ETA already past is deliberately included**: a shipment that should have landed and has not is exactly what this ought to surface, and nothing records an actual arrival to close it off. A blank ETA never counts. Each chip links to the register filtered **the way it counted**, so the number and the rows agree — measured, both links return exactly their two rows. The predicate moved to **`services/despatch.ts`** when it gained a third reader (the register's filter, the summary over it, and now this): a route importing a rule from another route is how the two come to disagree, the reason `receivables.ts` owns credit and `qc.ts` owns a pass. `DOCS_OUTSTANDING_D` joins `SEA_LEG`/`SEA_LEG_D` there.
- **Building it closed a hole under the chip that was already there.** The dashboard is mounted on the `dashboard` function, and `attention` was assembled wholesale — so **Sales and Production, which both hold `dispatch: none`, were told how many despatches were unbilled and then answered 404 on clicking the chip**. Measured before the gate: a Production login, which sees every order because the factory teams are unscoped, was handed the whole group's despatch count for a function it holds none of. That was pre-existing under `unbilledDespatches` alone, and two more chips would have made it three times the size, so it is closed rather than widened. All three figures now come from one `despatchAttention()` that returns **`{}` unless `allows(req, 'dispatch')`** — a figure the caller may not read is **absent, not zero**, the rule `customerSummary.ts` states, decided on the server because a copy of the access table on the client is a second policy and it drifts. It needed no client change at all: the keys were already optional (a server not yet redeployed omits them) and `AttentionChip` renders nothing for a missing count. Measured across all five logins on a scratch instance carrying three shipments and two lorries: Super Admin and Logistics get **unbilled 5, documents 2, arriving 2**; Sales and Production get the three keys **absent entirely**; Quality has no dashboard at all. Checked in a harness on the real route table both ways — the chips render with those counts and those links, and with the keys stripped no despatch chip is drawn while the rest of the strip is untouched.
- **The dashboard attention strip** gained overdue work orders, unbilled despatches, materials short and materials below reorder level. The two material counts are **group-wide and unscoped on purpose**: the store is not any one customer's, and a buyer needs the whole picture to raise one purchase order instead of several. The client types those four as optional, so a server that has not been redeployed yet yields zeros rather than `NaN`.
- **Delete guards multiplied**: an order now 409s if work orders or despatches reference it (both cascade on `order_id`, so without the guard a delete would silently take a day's production or a lorry-load with it). Same for a job with output or issued material, a PO with receipts, and any master something points at.

## Known gaps

Nothing outstanding from the original review.

Fixed while making the app deployable, and worth knowing the shape of:

- **Document numbers are unique**, enforced by indexes created in `db/connection.ts` — deliberately *not* in `schema.sql`, which runs first on every boot and would refuse to start on a database that already held duplicates. The migration de-duplicates (suffixing `-DUPn`) and then creates the index. Quotations key on `(number, revision)` since revisions share a number. `services/numbering.ts` claims the next number in one `INSERT … ON CONFLICT DO UPDATE … RETURNING` statement; the old read-then-update was only safe because SQLite serialises writes. A rejected number surfaces as a 409 from the central handler in `index.ts`, so every document type behaves the same.
- **Products**: read and create are open (an employee meeting a new product mid-quotation must not be blocked); `PUT`, `DELETE` and both import endpoints are manager-only, and delete now 409s when line items reference the product.
- **Follow-ups**: `POST` and `DELETE` are scoped like `PUT` already was.
- **Login is rate-limited** (`middleware/rateLimit.ts`) — in-memory by IP + email, which is correct for a single-instance deployment and is the piece to replace if that ever changes.
- **A password change ends every session signed under the old one.** `users.token_version` is bumped by `bumpTokenVersion()` and carried in the JWT by `signToken()`; `requireAuth` compares the two. Both live in `middleware/auth.ts` — routes never call `jwt.sign` directly any more, or a new login path would quietly issue unversioned tokens. **A token with no `tv` claim reads as version 0**, which is where every existing row starts, so adding the check signed nobody out; it only bites once a password has actually changed. The two callers differ on purpose: `POST /auth/change-password` bumps and then **hands the caller a fresh cookie**, so the browser doing the changing stays in while every other one drops out; `PUT /users/:id` with a password bumps **inside the same transaction as the hash** and hands back nothing, because the entire point of a manager resetting an account is that whoever holds it is signed out of it wherever they are. A profile edit carrying no password does not touch the version.
- **A 401 anywhere returns to the login screen.** `api/client.ts` calls a handler registered by `App.tsx`, which clears the user *and* the query cache — without the clear, the next person to sign in on that machine sees the previous one's customers until each query refetches. **Three 401s are excluded by URL** (`EXPECTS_401`): a failed login, a refused registration, and a wrong *current* password on the change-password form. Those are answers, not expiries; signing someone out for mistyping their old password would be a worse bug than the one this fixes. The handler reads the user through a ref, since it is registered once and would otherwise close over the mount-time value, which is always null.
